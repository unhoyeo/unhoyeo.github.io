애플리케이션을 개발하다 보면 "로그인 인증"과 같이 여러 컨트롤러에 걸쳐 공통적으로 적용해야 하는 기능들이 생긴다.

물론 모든 컨트롤러에 인증 로직을 일일이 추가할 수도 있지만 매우 비효율적이다.

또한 인증 정책이 변경될 때 모든 코드를 수정해야 하는 등 유지보수하기 어려워진다.

이처럼 여러 로직에 흩어져 있지만 하나의 단위로 관리되어야 하는 기능들을 <strong>공통 관심 사항(Cross-Cutting Concern)</strong>이라고 한다.

공통 관심 사항은 **스프링 AOP**로도 해결할 수 있다.

하지만 "웹"과 관련된 공통 관심 사항은 <strong>서블릿 필터</strong> 또는 <strong>스프링 인터셉터</strong>를 이용하는 것이 좋다.

필터와 인터셉터는 HTTP 헤더, URL 정보 등 웹 개발에 필요한 정보가 들어있는 **HttpServletRequest**를 제공하기 때문이다.

---

## 서블릿 필터 – 서블릿의 문지기

서블릿 필터는 서블릿 컨테이너에서 **요청과 응답의 흐름을 가로채서 전/후 공통 처리**를 수행할 수 있는 표준 인터페이스다.

즉, <strong>"문지기"</strong>와 같은 역할을 한다.

필터는 **체인(Chain) 구조**를 가지며, 여러 개의 필터가 순차적으로 적용된다.

예를 들어, 1번 필터에서 요청 로그를 남기고, 2번 필터에서 인증 체크를 하는 식이다.

**HTTP 요청 흐름**은 다음과 같다.

> HTTP 요청 → 서블릿 컨테이너(WAS) → **필터(1번 필터 → 2번 필터)** → 서블릿 → 컨트롤러

---

## 서블릿 필터의 특징

- **서블릿(DispatcherServlet) 실행 전**에 동작 (즉, 서블릿 컨테이너 레벨에서 HTTP 요청/응답을 필터링)
- 스프링 MVC에 의존하지 않음 (순수 서블릿 스펙)
- 모든 요청(정적 리소스 포함)에 대해 적용 가능
- 요청·응답 모두 가로채서 조작 가능 (ServletRequest, ServletResponse)
- 체인 구조(FilterChain)로 다중 필터 연결 가능

---

## Filter 인터페이스 (jakarta.servlet.Filter)

```java
public interface Filter {

    // 필터 초기화
    default void init(FilterConfig filterConfig) throws ServletException {}

    // 필터 로직 처리
    void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException;

    // 필터 종료 시 리소스 정리
    default void destroy() {}
}
```

- **init()**: 서블릿 컨테이너가 필터를 인스턴스화한 후 단 한 번만 호출함
- **doFilter()**:
  - 클라이언트 요청으로 인해 요청/응답 쌍이 체인을 통해 전달될 때마다 컨테이너에 의해 호출됨 (매 요청마다 호출)
  - 이 메서드에 전달된 FilterChain을 통해 요청과 응답을 필터 체인의 다음 엔티티로 전달할 수 있음
  - 일반적으로 다음과 같은 패턴으로 필터 로직을 구현함:
    1. 요청 검사
    2. 입출력 필터링(콘텐츠 또는 헤더 필터링)을 위해 커스텀 구현체로 요청/응답 객체를 래핑
    3. FilterChain 객체(chain.doFilter())를 사용하여 체인의 다음 엔티티를 호출하거나, 요청 처리를 차단하기 위해 요청/응답 쌍을 필터 체인의 다음 엔티티로 전달하지 않음
    4. 필터 체인의 다음 엔티티를 호출한 후, 응답에 직접 헤더를 설정
- **destroy()**: 필터가 컨테이너에서 제거될 때(서블릿 컨테이너가 종료될 때) 단 한 번만 호출함

---

## chain.doFilter()

- 호출 시 다음 단계(필터 또는 서블릿)로 요청이 전달되지만, 호출하지 않으면 요청 처리가 **거기서 중단됨**
- 이 특징 덕분에 미인증 사용자의 요청을 컨트롤러에 도달하기 전에 차단하고, 로그인 페이지로 리다이렉트 시킬 수 있음

---

## 요청 로그 필터 구현 예시

```java
@Slf4j
@WebFilter(urlPatterns = "/*") // 필터 등록
public class LogFilter implements Filter {

    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
        log.info("log filter init");
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        // HTTP 요청이 아닌 경우를 고려한 ServletRequest를 HttpServletRequest로 변환
        HttpServletRequest httpRequest = (HttpServletRequest) request;

        String uuid = UUID.randomUUID().toString(); // HTTP 요청을 구분하기 위한 임의의 값
        String requestURI = httpRequest.getRequestURI(); // 요청 URI

        try {
            log.info("REQUEST [{}][{}]", uuid, requestURI);
            // 다음 단계 진행을 위해서 필수로 호출 (다음 필터가 있으면 해당 필터를 호출하고, 없으면 서블릿을 호출)
            chain.doFilter(request, response);
        } catch (Exception e) {
            throw e;
        } finally {
            log.info("RESPONSE [{}][{}]", uuid, requestURI);
        }
    }

    @Override
    public void destroy() {
        log.info("log filter destroy");
    }
}
```

Filter 인터페이스를 구현해서 **@WebFilter**를 통해 등록하면, 서블릿 컨테이너가 해당 필터를 싱글톤 객체로 생성하고 관리한다.

하지만 필터 실행 순서를 조절할 수 없기 때문에, 다음과 같이 **FilterRegistrationBean**을 사용해서 직접 빈으로 등록하는 것을 권장한다.

```java
@Bean
public FilterRegistrationBean<LogFilter> logFilter() {
    FilterRegistrationBean<LogFilter> registrationBean = new FilterRegistrationBean<>();
    registrationBean.setFilter(new LogFilter());
    registrationBean.addUrlPatterns("/*"); // 모든 요청에 대해 실행
    registrationBean.setOrder(1); // 필터 실행 순서 (낮을수록 우선)
    return registrationBean;
}
```

> 더 알아보기: logback MDC (같은 요청이면 같은 식별자로 로그 남기기)

## 인증 필터 구현 예시

```java
@Slf4j
public class LoginCheckFilter implements Filter {

    private static final String[] whitelist = {"/", "/signup", "/login", "/logout", "/css/*"};

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;

        String requestURI = httpRequest.getRequestURI();

        try {
            log.info("인증 체크 필터 시작 {}", requestURI);
            if (isLoginCheckPath(requestURI)) {
                log.info("인증 체크 로직 실행 {}", requestURI);
                HttpSession session = httpRequest.getSession(false);

                // 로그인하지 않은 사용자
                if (session == null || session.getAttribute("loginMember") == null) {
                    log.info("미인증 사용자 요청 {}", requestURI);
                    // 로그인 페이지로 리다이렉트
                    httpResponse.sendRedirect("/login?redirectURL=" + requestURI);
                    return; // 미인증 사용자는 다음 단계로 진행하지 않고 중단
                }
            }
            // 다음 단계로 진행
            chain.doFilter(request, response);
        } catch (Exception e) {
            throw e; // 예외 로깅 가능 하지만, 서블릿 컨테이너까지 예외를 전달해야 함
        } finally {
            log.info("인증 체크 필터 종료 {}", requestURI);
        }
    }

    private boolean isLoginCheckPath(String requestURI) {
        // 화이트 리스트는 로그인 체크하지 않음
        return !PatternMatchUtils.simpleMatch(whitelist, requestURI);
    }
}
```

- whitelist: **로그인 없이도 접근 가능한 URL**(홈, 회원가입, 로그인 페이지, css 리소스 등)
  - whitelist에 포함되지 않은 경로로 요청이 들어오면 무조건 인증 체크
- 인증 체크 시, 세션에 로그인 정보가 없을 경우(로그인하지 않은 사용자):
  - 사용자가 원래 가려던 경로를 쿼리 파라미터(redirectURL)로 포함하여 로그인 페이지로 리다이렉트 시킴
  - chain.doFilter()를 호출하지 않고 **바로 반환** → 서블릿/컨트롤러를 호출하지 않음
- LoginCheckFilter 등록 시:
  - LogFilter 다음에 실행되기 위해 <strong>setOrder(2)</strong>로 등록 (우선순위: LogFilter(1) > LoginCheckFilter(2))

## 스프링 인터셉터 – 스프링 MVC에 특화된 문지기

스프링 인터셉터는 서블릿 필터와 거의 유사하지만, 스프링 MVC가 제공하는 기술이기 때문에 **호출 순서**에 차이가 있다.

> HTTP 요청 → 서블릿 컨테이너(WAS) → 필터 → 서블릿(DispatcherServlet) → **인터셉터(1번 → 2번)** → 컨트롤러

또한 서블릿 필터보다 더 다양한 기능을 제공한다.

---

## 스프링 인터셉터의 특징

- DispatcherServlet 실행 후, HandlerMapping에서 **컨트롤러(핸들러) 호출 직전**에 동작
- 즉, 스프링 MVC의 요청 처리 흐름 내부에서 동작
- 스프링 MVC에 의존 (HandlerInterceptor 인터페이스)
- 더 정교한 호출 시점 제공 (컨트롤러 실행 전/후, View 렌더링 후)
- 스프링 MVC와 관련된 정보 제공 (어떤 컨트롤러가 호출되는지(HandlerMethod), 어떤 ModelAndView가 반환되는지 등)
- 정적 리소스 요청은 기본적으로 제외됨(설정 가능)

---

## HandlerInterceptor 인터페이스

```java
public interface HandlerInterceptor {

    // 컨트롤러 호출 전 (false 리턴 시 이후 과정 중단됨)
    default boolean preHandle(HttpServletRequest request,
                              HttpServletResponse response,
                              Object handler) throws Exception {
        return true;
    }

    // 컨트롤러 호출 후 (뷰 렌더링되기 전)
    default void postHandle(HttpServletRequest request,
                            HttpServletResponse response,
                            Object handler,
                            @Nullable ModelAndView modelAndView) throws Exception {
    }

    // 뷰 렌더링까지 완료된 후 (예외 발생 여부와 상관 없이 항상 호출)
    default void afterCompletion(HttpServletRequest request,
                                 HttpServletResponse response,
                                 Object handler,
                                 @Nullable Exception ex) throws Exception {
    }
}
```

인터셉터는 필터의 doFilter()와 달리, 호출 시점이 명확하게 **세 단계**로 나뉜다.

- **preHandle**:
  - **핸들러 실행 전** 호출
  - HandlerMapping이 적절한 핸들러 객체를 결정한 후, HandlerAdapter가 해당 핸들러를 호출하기 전에 호출한다.
  - DispatcherServlet은 실행 체인에 포함된 핸들러를 처리하는데, 실행 체인은 여러 개의 인터셉터로 구성되며, 핸들러 자체는 마지막에 위치한다.
  - 반환 값을 통해 각 인터셉터는 실행 체인을 중단할지 여부를 결정할 수 있다. (true: 진행, false: 중단)
- **postHandle**:
  - **핸들러 실행 성공 후** 호출
  - HandlerAdapter가 실제로 핸들러를 호출한 후, DispatcherServlet이 뷰를 렌더링하기 전에 호출한다.
  - 지정된 ModelAndView를 통해 뷰에 추가적인 모델 객체를 전송할 수 있다.
  - 실행 체인의 여러 개의 인터셉터가 역순으로 적용되어, 후처리를 할 수 있다.
- **afterCompletion**:
  - **뷰 렌더링 후**(요청 처리 완료 후) 호출
  - 핸들러 실행 결과에 따라 호출되므로 적절한 리소스 정리를 할 수 있다.
  - 해당 인터셉터의 preHandle 메서드가 성공적으로 완료되고 true를 반환한 경우에만 호출된다.
  - postHandle 메서드와 마찬가지로, 체인의 각 인터셉터에서 역순으로 호출되므로, 첫 번째 인터셉터가 마지막으로 호출된다.
  - **예외 발생 여부와 관계없이 항상 호출**된다. (예외 정보를 파라미터로 받음)

- **메서드 실행 순서**:

> ... → Filter → DispatcherServlet → Interceptor(preHandle) → Controller → Interceptor(postHandle) → View → Interceptor(afterCompletion) → Filter → ...

## 요청 로그 인터셉터 구현 예시

```java
@Slf4j
public class LogInterceptor implements HandlerInterceptor {

    public static final String LOG_ID = "logId";

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) throws Exception {

        String requestURI = request.getRequestURI(); // 요청 URI
        String logId = UUID.randomUUID().toString(); // HTTP 요청을 구분하기 위한 임의의 값

        // 해당 logId를 다른 메서드에서도 사용하기 위해 request 객체에 보관
        request.setAttribute(LOG_ID, logId);

        log.info("REQUEST [{}][{}][{}]", logId, requestURI, handler);

        // 진행 여부 반환 (true: 진행, false: 중단)
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest request,
                           HttpServletResponse response,
                           Object handler,
                           ModelAndView modelAndView) throws Exception {

        log.info("postHandle [{}]", modelAndView);
    }

    @Override
    public void afterCompletion(HttpServletRequest request,
                                HttpServletResponse response,
                                Object handler,
                                Exception ex) throws Exception {

        String requestURI = request.getRequestURI();
        String logId = (String) request.getAttribute(LOG_ID);

        log.info("RESPONSE [{}][{}]", logId, requestURI);

        if (ex != null) {
            log.error("afterCompletion exception", ex);
        }
    }
}
```

- 서블릿 필터는 요청/응답 로그를 모두 doFilter()에서 남겼지만, 스프링 인터셉터는 **호출 시점이 분리**되어 있음
  - 즉, 요청 로그는 preHandle()에서, 응답 로그는 afterCompletion()에서 남겨야 함
- ⚠️ 인터셉터는 기본적으로 싱글톤으로 관리되므로, **필드에 요청별 데이터를 저장하면 안 됨**(동시성 문제)
  - 따라서 두 메서드에서 같은 값(logId)을 공유하려면, HttpServletRequest 객체에 보관해야 함

> handler 객체는 어떤 HandlerMapping을 사용하는지에 따라 달라진다.
> 예를 들어, RequestMappingHandlerMapping의 경우 **HandlerMethod** 객체가 넘어오고,
> 정적 리소스 요청의 경우 **ResourceHttpRequestHandler** 객체가 넘어온다.

## 인증 인터셉터 구현 예시

```java
@Slf4j
public class LoginCheckInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) throws Exception {

        String requestURI = request.getRequestURI();
        log.info("인증 체크 인터셉터 실행 {}", requestURI);

        HttpSession session = request.getSession(false);
        if (session == null || session.getAttribute("loginMember") == null) {
            log.info("미인증 사용자 요청");
            response.sendRedirect("/login?redirectURL=" + requestURI);
            return false; // 로그인하지 않은 사용자 → 중단
        }
        return true; // 로그인 사용자 → 계속 진행
    }
}
```

- 인증은 컨트롤러 호출 전에만 하면 되므로, preHandle() 메서드만 구현하면 된다.

## 인터셉터 등록 – WebMvcConfigurer

인터셉터는 WebMvcConfigurer가 제공하는 **addInterceptors()** 메서드를 통해 등록할 수 있다.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LogInterceptor())
                .order(1)
                .addPathPatterns("/**")
                .excludePathPatterns("/css/**", "/*.ico", "/error");

        registry.addInterceptor(new LoginCheckInterceptor())
                .order(2)
                .addPathPatterns("/**")
                .excludePathPatterns(
                        "/", "/signup", "/login", "/logout",
                        "/css/**", "/*.ico", "/error"
                );
    }
}
```

다음 메서드를 통해 서블릿 필터보다 훨씬 정밀한 URL 패턴을 적용할 수 있다.

- **addPathPatterns**: 인터셉터를 적용할 URL 패턴
- **excludePathPatterns**: 인터셉터를 제외할 URL 패턴

또한 서블릿이 제공하는 URL 경로가 아닌, 스프링이 제공하는 URL 경로를 적용하기 때문에 더욱 세밀하게 URL 패턴을 설정할 수 있다.

```html
PathPattern은 다음 규칙을 사용하여 URL 경로를 일치시킵니다.

              ? = 한 문자와 일치
              * = 경로 세그먼트 내에서 0개 이상의 문자와 일치
             ** = 경로 끝까지 0개 이상의 경로 세그먼트와 일치
       {spring} = 경로 세그먼트와 일치하여 "spring"이라는 변수로 캡처
{spring:[a-z]+} = 정규 표현식 [a-z]+를 경로 세그먼트와 일치하여 "spring"이라는 경로 변수로 캡처
      {*spring} = 경로 끝까지 0개 이상의 경로 세그먼트와 일치하여 "spring"이라는 변수로 캡처

참고: AntPathMatcher와 달리 **는 패턴 끝에서만 지원됩니다.
예를 들어 /pages/{**}는 유효하지만, /pages/{**}/details는 유효하지 않습니다.
캡처링 변형 {*spring}에도 동일하게 적용됩니다.
이는 패턴을 비교할 때 특정성을 위해 모호성을 제거하기 위한 것입니다.

예시
/pages/t?st.html → /pages/test.html 및 /pages/tXst.html과 일치하지만,
                   /pages/toast.html과는 일치하지 않습니다.

/resources/*.png → 리소스 디렉터리의 모든 .png 파일과 일치합니다.

/resources/** → /resources/image.png 및 /resources/css/spring.css를 포함하여
                /resources/ 경로 아래의 모든 파일과 일치합니다.

/resources/{*path} → /resources/ 및 /resources 아래의 모든 파일과 일치하며,
                     "path"라는 변수에 상대 경로를 저장합니다.
                     /resources/image.png는 "path" → "/image.png"와 일치하고,
                     /resources/css/spring.css는 "path" → "/css/spring.css"와 일치합니다.

/resources/{filename:\\w+}.dat → /resources/spring.dat와 일치하고
                                 파일 이름 변수에 "spring" 값을 할당합니다.
```

> 출처는 [여기](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/util/pattern/PathPattern.html)

## 서블릿 필터 vs 스프링 인터셉터 비교

|  |  |  |
| --- | --- | --- |
| **구분** | **서블릿 필터** | **스프링 인터셉터** |
| 실행 위치 | DispatcherServlet 전 | DispatcherServlet 후, 컨트롤러 전/후 |
| 기술 기반 | 서블릿 표준 | 스프링 MVC |
| 적용 범위 | 모든 요청 (정적 리소스 포함) | 스프링 MVC 요청 (정적 리소스 제외) |
| 의존 객체 | ServletRequest, ServletResponse | HttpServletRequest, HttpServletResponse, HandlerMethod, ModelAndView |
| 주요 목적 | 저수준 요청/응답 가공, 전역 처리 | 컨트롤러 호출 전후 전처리/후처리 |
| 장점 | 프레임워크 비의존적, 범용적 | MVC 객체 접근 가능, 세밀한 제어 |
| 단점 | MVC 정보 없음 | MVC 요청만 처리 가능 |

## ArgumentResolver로 컨트롤러 코드 간소화

이전에 배운 ArgumentResolver를 활용하면, 로그인한 사용자 정보를 컨트롤러에서 반복적으로 조회하는 코드를 깔끔하게 만들 수 있다.

**@Login**과 같은 **커스텀 애노테이션**을 만들고, 이 애노테이션이 붙은 파라미터를 처리할 ArgumentResolver를 직접 구현하는 방식이다.

```java
@Target(ElementType.PARAMETER) // 파라미터에서만 사용
@Retention(RetentionPolicy.RUNTIME) // 리플렉션 등을 활용할 수 있도록 런타임까지 남아있음
public @interface Login {
}
```

```java
public class LoginMemberArgumentResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        // @Login 애노테이션 유무
        boolean hasLoginAnnotation = parameter.hasParameterAnnotation(Login.class);
        // Member 타입 유무
        boolean isMemberType = Member.class.isAssignableFrom(parameter.getParameterType());
        return hasLoginAnnotation && isMemberType;
    }

    @Override
    public Object resolveArgument(MethodParameter parameter,
                                  ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest,
                                  WebDataBinderFactory binderFactory) throws Exception {

        HttpServletRequest request = (HttpServletRequest) webRequest.getNativeRequest();

        HttpSession session = request.getSession(false);
        if (session == null) return null;

        // 컨트롤러에 member 객체를 넘겨줌
        return session.getAttribute("loginMember");
    }
}
```

- **supportsParameter()**: @Login 애노테이션이 있고, 파라미터 타입이 Member 클래스인 경우에만 ArgumentResolver가 동작
- **resolveArgument()**: 실제 처리 로직 (세션에서 로그인 회원 정보를 조회하여 반환)

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    // LoginMemberArgumentResolver 등록
    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new LoginMemberArgumentResolver());
    }
    ...
}
```

```java
@GetMapping("/")
public String home(@Login Member loginMember, Model model) {
    // 로그인하지 않은 사용자
    if (loginMember == null) {
        return "home";
    }
    // 로그인 사용자
    model.addAttribute("member", loginMember);
    return "loginHome";
}
```

- 컨트롤러에서는 세션 조회 코드 없이 파라미터에 @Login 선언만으로 로그인된 사용자 정보를 주입받을 수 있음
