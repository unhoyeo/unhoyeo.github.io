> **스프링 컨테이너의 생성 과정**

저번 글에서는 **순수한 자바**만으로 DI를 적용했다. 이제 AppConfig를 스프링 기반으로 변경해 보자.

```java
@Configuration
public class AppConfig {

    @Bean
    public MemberService memberService() {
       return new MemberServiceImpl(memberRepository());
    }

    @Bean
    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }
}
```

AppConfig에 설정을 구성한다는 뜻의 **@Configuration**을 붙여주고, 각 메서드에 **@Bean**을 붙여준다.

실제로 사용하는 예시를 보자.

```java
public class MemberApp {
    public static void main(String[] args) {
//       AppConfig appConfig = new AppConfig();
//       MemberService memberService = appConfig.memberService();

       ApplicationContext ac = new AnnotationConfigApplicationContext(AppConfig.class);
       MemberService memberService = ac.getBean("memberService", MemberService.class);

       ...
```

기존에는 일단 AppConfig 객체를 생성한 후, MemberService 객체를 **appConfig의 memberService()** 메서드를 통해 받아왔다.

이제는 **ApplicationContext**라는 것을 생성한 후, **getBean()**이라는 메서드를 통해 memberService 객체를 받아온다.

여기서 ApplicationContext를 **"스프링 컨테이너"**라고 한다. 스프링 컨테이너를 생성할 때는 **설정 정보**를 지정해주어야 한다. 여기서는 **@Configuration을 붙였던 AppConfig 클래스**를 설정 정보로 지정했다.

> ApplicationContext는 인터페이스이고, AnnotationConfigApplicationContext이 구현체이다.
> 스프링 컨테이너는 XML 기반으로 만들 수도 있고, 애노테이션 기반의 자바 설정 클래스로 만들 수도 있다.

스프링 컨테이너는 파라미터로 넘어온 설정 클래스에서 **"@Bean이 붙은 메서드"를 호출해서 반환된 객체를 모두 스프링 컨테이너에 등록**하는데, 이렇게 스프링 컨테이너에 등록된 객체를 **"스프링 빈"**이라 한다.

> 스프링 빈은 스프링 컨테이너 안에 있는 **스프링 빈 저장소**에 **{key=빈 이름, value=빈 객체}** 형태로 등록된다.
> 빈 이름은 기본적으로 **@Bean이 붙은 메서드 이름**으로 정해진다.
> 빈 이름을 직접 임의로 정할 수도 있지만, 이름이 중복될 경우 다른 빈이 무시되거나 기존 빈을 덮어버릴 수 있다.

스프링 빈을 등록한 후, 스프링 컨테이너는 **설정 정보를 참고**해서 **의존관계를 주입(DI)**한다.

> 원래 스프링은 **빈을 생성**하고, **의존관계를 주입**하는 단계가 나누어져 있다.
> 하지만 이렇게 자바 코드로 **직접 스프링 빈을 등록**할 경우, 생성자를 호출할 때 의존관계 주입도 **한 번에 처리**된다.

기존에는 개발자가 직접 AppConfig를 사용해서 객체를 생성하고, DI하고, 조회했지만, 이제는 스프링 컨테이너에 객체를 스프링 빈으로 등록하고, 스프링 컨테이너에서 스프링 빈을 찾아서 사용하도록 변경되었다. 코드가 약간 더 복잡해진 것 같은데 어떤 장점이 있어서 스프링 컨테이너를 사용할까? 이것은 나중에 알아보고, 지금은 스프링 빈을 조회하는 여러 방법들을 알아보자.

> **스프링 빈 조회**

```java
// 빈 이름으로 조회
MemberRepository memberRepository = ac.getBean("memberRepository");

// 빈 타입으로 조회
MemberRepository memberRepository = ac.getBean(MemberRepository.class);

// 빈 이름과 빈 타입으로 조회
MemberRepository memberRepository = ac.getBean("memberRepository", MemberRepository.class);

// 구체 타입으로 조회
MemberRepository memberRepository = ac.getBean("memberRepository", MemoryMemberRepository.class);
```

만약 찾는 빈이 없다면 **NoSuchBeanDefinitionException** 예외가 발생한다.

> NoSuchBeanDefinitionException: No bean named 'xxx' available

타입으로 조회 시 **같은 타입의 빈이 둘 이상**이거나, **자식 빈이 둘 이상**일 경우 **NoUniqueBeanDefinitionException** 예외가 발생한다.

> NoUniqueBeanDefinitionException: No qualifying bean of type 'com.spring.study.MemberRepository' available: expected single matching bean but found 2: memberRepository1,memberRepository2

이때는 간단하게 **빈 이름을 지정**하면 된다.

```
MemberRepository memberRepository = ac.getBean("memberRepository1", MemberRepository.class);
```

자식이 둘 이상일 경우, 좋은 방법은 아니지만 **구체 타입**으로 조회해도 해결할 수 있다.

```java
MemberRepository memberRepository = ac.getBean("memberRepository", MemoryMemberRepository.class);
```

---

**해당 타입의 모든 빈** 또는 **해당 타입의 모든 자식 빈**은 **ac.getBeansOfType()** 메서드를 통해 조회할 수 있다.

```java
Map<String, MemberRepository> beansOfType = ac.getBeansOfType(MemberRepository.class);

for (String key : beansOfType.keySet()) {
    System.out.println("key = " + key + " value = " + beansOfType.get(key));
}
```

> 반환값은 Map 타입으로, {key=빈 이름, value=빈 객체} 형태이다.

> Object 타입은 모든 객체의 부모 타입이므로, **Object** 타입으로 조회하면 **모든 빈**이 조회된다.

마지막으로, 스프링에 등록된 **모든 빈의 이름**은 **ac.getBeanDefinitionNames()** 메서드를 통해 조회할 수 있다.

```java
// getBeanDefinition() 메서드를 사용하려면 ac의 타입을 AnnotationConfigApplicationContext으로 해야 한다.
AnnotationConfigApplicationContext ac = new AnnotationConfigApplicationContext(AppConfig.class);

String[] beanDefinitionNames = ac.getBeanDefinitionNames(); // 모든 빈 이름

for (String beanDefinitionName : beanDefinitionNames) {
    BeanDefinition beanDefinition = ac.getBeanDefinition(beanDefinitionName); // 빈 설정 메타정보

    // 내가 직접 등록한 빈일 경우
    if (beanDefinition.getRole() == BeanDefinition.ROLE_APPLICATION) {
        Object bean = ac.getBean(beanDefinitionName); // 빈 객체 조회
        System.out.println("name = " + beanDefinitionName + ", object = " + bean);
    }
}
```

> BeanDefinition.**ROLE\_APPLICATION** : 직접 등록한 애플리케이션 빈
> BeanDefinition.**ROLE\_INFRASTRUCTURE** : 스프링이 내부에서 사용하는 빈

> **빈 설정 메타정보 - BeanDefinition**

위에서 스프링 컨테이너는 XML 기반으로 만들 수도 있고, 애노테이션 기반의 자바 설정 클래스로 만들 수도 있다고 했다.

스프링은 어떻게 다양한 설정 형식을 지원하는 것일까? 그 중심에는 **BeanDefinition**이라는 **추상화**가 있다.

쉽게 말해서 **역할과 구현을 나눈 것**이다. **스프링 컨테이너는 오직 BeanDefinition에만 의존한다.** XML인지 자바 코드인지는 몰라도 된다. 그저 XML을 읽어서 BeanDefinition을 만들거나 자바 코드를 읽어서 BeanDefinition을 만들면 되는 것이다.

이때 BeanDefinition을 **"빈 설정 메타정보"**라 한다.

**@Bean** 또는 **&lt;bean> 당 각각 하나씩 메타 정보가 생성**되고, **스프링 컨테이너**는 이 **빈 설정 메타정보를 기반으로 스프링 빈을 생성**한다.

> beanDefinitionName = appConfig
> beanDefinition = Generic bean: class [com.spring.study.AppConfig$$SpringCGLIB$$0]; scope=singleton; abstract=false; lazyInit=null; autowireMode=0; dependencyCheck=0; autowireCandidate=true; primary=false; factoryBeanName=null; factoryMethodName=null; initMethodNames=null; destroyMethodNames=null
>
> beanDefinitionName = memberService
> beanDefinition = Root bean: class [null]; scope=; abstract=false; lazyInit=null; autowireMode=3; dependencyCheck=0; autowireCandidate=true; primary=false; factoryBeanName=appConfig; factoryMethodName=memberService; initMethodNames=null; destroyMethodNames=[(inferred)]; defined in com.spring.study.AppConfig
>
> beanDefinitionName = memberRepository
> beanDefinition = Root bean: class [null]; scope=; abstract=false; lazyInit=null; autowireMode=3; dependencyCheck=0; autowireCandidate=true; primary=false; factoryBeanName=appConfig; factoryMethodName=memberRepository; initMethodNames=null; destroyMethodNames=[(inferred)]; defined in com.spring.study.AppConfig

- beanClassName: 생성할 빈의 클래스명(자바 설정처럼 팩토리 역할의 빈을 사용하면 없음)
- scope: 빈 생명주기 (기본값: 싱글톤)
- lazyInit: 스프링 컨테이너를 생성할 때 빈을 생성하는 것이 아니라, 실제 빈을 사용할 때까지 생성을 지연하는지 여부
- factoryBeanName: 팩토리 역할의 빈을 사용할 경우 이름 (예: appConfig)
- factoryMethodName: 빈을 생성할 팩토리 메서드 지정 (예: memberService)
- InitMethodNames: 빈을 생성하고, 의존관계를 적용한 뒤에 호출되는 초기화 메서드명
- destroyMethodNames: 빈의 생명주기가 끝나서 제거하기 직전에 호출되는 메서드명
- constructor arguments, properties: 의존관계 주입에서 사용한다. (자바 Config처럼 팩토리 역할의 빈을 사용하면 없음)

> 스프링 빈을 등록하는 방법은 크게 XML 파일을 이용해 **직접 스프링 빈을 등록**하는 방법과, **팩토리 빈을 통해서 등록**하는 방법이 있다.
> 일반적으로 **자바 Config**를 사용하는 것은 **팩토리 빈**을 통해서 등록하는 방법이다.

> **BeanFactory**

BeanFactory는 **스프링 컨테이너의 최상위 인터페이스**다. **getBean()** 메서드를 제공하며, 스프링 빈을 **관리**하고 **조회**하는 역할을 담당한다. 지금까지 우리가 사용했던 대부분의 기능은 BeanFactory가 제공하는 기능이다. 그렇다면 ApplicationContext와의 차이점은 뭘까?

ApplicationContext는 BeanFactory의 기능을 모두 상속받아서 제공할 뿐만 아니라, 다른 인터페이스들도 상속받아서 애플리케이션을 개발할 때 필요한 수많은 **부가기능**을 제공한다.

- **메시지 소스를 활용한 국제화 기능**: 한국에서 들어오면 한국어로, 영어권에서 들어오면 영어로 출력
- **환경변수**: 로컬, 개발, 운영 등을 구분해서 처리
- **애플리케이션 이벤트**: 이벤트를 발행하고 구독하는 모델을 편리하게 지원
- **편리한 리소스 조회**: 파일, 클래스패스, 외부 등에서 리소스를 편리하게 조회
