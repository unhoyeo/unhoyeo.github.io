현대 웹 애플리케이션 개발에서 **하드코딩된 텍스트**는 유지보수의 가장 큰 적 중 하나다.

간단한 문구 하나를 변경하기 위해 수많은 HTML 파일을 수정해야 하는 상황은 비효율적일 뿐만 아니라 실수를 유발하기 쉽다.

스프링은 이러한 문제를 해결하기 위해 유연한 메시지 관리 및 **국제화(Internationalization, i18n)** 기능을 제공한다.

---

## 메시지 기능이 왜 필요할까?

"상품명"이라는 단어를 모두 "상품 이름"으로 바꿔달라는 기획자의 갑작스러운 요청을 받았다고 가정해 보자.

만약 모든 텍스트가 HTML 파일에 하드코딩되어 있다면, 개발자는 관련된 모든 파일을 열어 일일이 수작업으로 변경해야 한다.

이는 매우 번거롭고 누락의 위험이 크다.

```html
<label for="itemName">상품명</label>  <!-- 상품명 → 상품 이름 -->
```

하지만 메시지 기능을 적용하면 화면에 표시되는 모든 텍스트(UI 문자열)를 한 곳에서 중앙 집중적으로 관리할 수 있다.

```html
<label for="itemName" th:text="#{label.itemName}"></label>

# messages.properties
label.itemName=상품명
```

이제 "상품명"을 "상품 이름"으로 바꾸고 싶다면 messages.properties 파일만 수정하면 애플리케이션 전체에 일괄적으로 반영된다.

이로써 코드와 텍스트가 완벽하게 분리되어 유지보수성이 극대화된다.

---

## 메시지 기능 설정 및 국제화

스프링은 메시지 관리를 위해 **MessageSource**라는 핵심 인터페이스를 제공한다.

과거에는 해당 인터페이스의 구현체인 ResourceBundleMessageSource를 직접 스프링 빈으로 등록해야 했지만,

스프링 부트를 사용하면 해당 과정을 모두 자동으로 해준다.

따라서 스프링 부트 사용 시 application.properties에 다음과 같이 간단한 설정을 통해 메시지 소스를 설정할 수 있다.

```python
# 여러 경로의 메시지 파일을 인식하도록 설정. 기본값은 'messages'
spring.messages.basename=messages,config.i18n.messages
```

또한 아무런 설정을 하지 않아도 스프링 부트는 기본적으로 spring.messages.basename=messages로 동작한다.

따라서 resources 폴더 아래에 messages.properties 파일을 두기만 하면 즉시 메시지 기능을 사용할 수 있다.

여기서 한 발 더 나아가, messages.properties를 기본 파일과 특정 언어 파일로 따로 생성하여 국제화를 적용할 수도 있다.

/resources/messages.properties

```python
# 기본 파일 (한글)
hello=안녕
hello.name=안녕 {0}
```

/resources/messages\_en.properties

```python
# 특정 언어 파일 (영어)
hello=hello
hello.name=hello {0}
```

## MessageSource 인터페이스

MessageSource 인터페이스의 getMessage() 메서드는 메시지를 조회하는 핵심 API다.

```java
public interface MessageSource {
    // 코드가 없을 때 기본 메시지 지정 가능
    String getMessage(String code,
                      @Nullable Object[] args,
                      @Nullable String defaultMessage,
                      Locale locale);

    // 코드가 없으면 예외 발생
    String getMessage(String code,
                      @Nullable Object[] args,
                      Locale locale) throws NoSuchMessageException;
}
```

- **code**: 메시지 파일의 키 (hello, hello.name 등)
- **args**: 메시지에 포함될 파라미터 ({0}, {1} 등에 전달할 값 배열)
- **defaultMessage**: 코드를 찾지 못했을 때 반환할 기본 텍스트
- **locale**: 어떤 언어의 메시지를 가져올지 지정 (Locale.KOREA, Locale.ENGLISH 등)

실제 사용 예시:

```java
@SpringBootTest
class MessageSourceTest {

    @Autowired
    MessageSource ms;

    @Test
    void helloMessage() {
        // locale이 null이면 기본 메시지 파일(messages.properties)을 사용
        assertThat(ms.getMessage("hello", null, null)).isEqualTo("안녕");
    }

    @Test
    void notFoundMessageCode() {
        // 코드가 없으면 NoSuchMessageException 예외 발생
        assertThatThrownBy(() -> ms.getMessage("no_code", null, null))
                .isInstanceOf(NoSuchMessageException.class);

        // 기본 메시지를 지정하면 예외 대신 기본 메시지가 반환
        String result = ms.getMessage("no_code", null, "기본 메시지", null);
        assertThat(result).isEqualTo("기본 메시지");
    }

    @Test
    void argumentMessage() {
        // {0} 위치에 "Spring" 파라미터 전달 (hello.name=안녕 {0})
        String result = ms.getMessage("hello.name", new Object[]{"Spring"}, null);
        assertThat(result).isEqualTo("안녕 Spring");
    }

    @Test
    void englishMessage() {
        // locale을 ENGLISH로 지정하여 messages_en.properties 파일 사용
        assertThat(ms.getMessage("hello", null, Locale.ENGLISH)).isEqualTo("hello");
    }
}
```

## 타임리프와의 연동

타임리프는 스프링의 MessageSource와 완벽하게 통합되어 있다.

타임리프의 메시지 표현식 <strong>#{...}</strong>을 사용하면 현재 Locale에 맞는 메시지를 자동으로 가져와 렌더링한다.

```html
<h1 th:text="#{page.items}">상품 목록</h1>

<button type="button" th:text="#{button.save}">저장</button>
```

메시지의 파라미터는 다음과 같이 사용할 수 있다.

```html
hello.name=안녕 {0}

<p th:text="#{hello.name(${item.itemName})}"></p>
```

## 국제화(i18n)의 원리 – Locale 기반 메시지 선택

국제화의 핵심은 사용자의 Locale 정보에 따라 적절한 메시지 파일을 동적으로 선택하는 것이다.

스프링은 매우 체계적인 폴백(Fallback) 전략을 따른다.

예를 들어, 사용자의 Locale이 **en\_US**(미국 영어)일 경우, 스프링은 다음 순서로 메시지 파일을 찾는다.

1. messages<strong>\_en\_US</strong>.properties (가장 구체적인 파일)
2. messages<strong>\_en</strong>.properties (언어만 일치하는 파일)
3. messages.properties (기본 파일)

⚠️ 만약 Locale 정보가 없는 경우(null), Locale.getDefault()를 호출하여 시스템의 기본 Locale을 사용한다.

---

## 스프링이 Locale을 결정하는 방법 – LocaleResolver

스프링은 LocaleResolver 인터페이스를 통해 현재 요청에 대한 Locale을 결정한다.

```java
public interface LocaleResolver {

    Locale resolveLocale(HttpServletRequest request);

    void setLocale(HttpServletRequest request,
                   @Nullable HttpServletResponse response,
                   @Nullable Locale locale);
}
```

스프링 부트는 LocaleResolver의 기본 구현체로 **AcceptHeaderLocaleResolver**를 사용한다.

이 구현체는 HTTP 요청 헤더의 **Accept-Language** 값을 읽어 Locale을 결정한다.

예를 들어 크롬 브라우저의 언어 설정이 영어, 한국어 순으로 되어 있다면,

Accept-Language 헤더에는 en, ko-KR;q=0.9, ko;q=0.8와 같은 값이 담겨 서버로 전송된다.

AcceptHeaderLocaleResolver는 이 값을 해석하여 가장 우선순위가 높은 en을 Locale로 선택하고,

그 결과 messages\_en.properties 파일이 사용된다.

## LocaleResolver 커스터마이징

기본 구현체인 AcceptHeaderLocaleResolver는 사용자가 브라우저 설정을 직접 바꾸지 않는 한 언어를 변경할 수 없다.

실무에서는 사용자가 웹사이트 내에서 직접 언어를 선택(예: 헤더의 언어 선택 드롭다운)하는 기능이 필요한 경우가 많다.

이때는 다른 LocaleResolver 구현체를 사용하도록 변경해야 한다.

- **SessionLocaleResolver**: 사용자가 선택한 Locale 정보를 세션에 저장 (브라우저를 닫으면 초기화됨)
- **CookieLocaleResolver**: 사용자가 선택한 Locale 정보를 쿠키에 저장 (브라우저를 닫았다가 다시 열어도 선택한 언어가 유지됨)

예를 들어 CookieLocaleResolver를 사용하려면, 다음과 같이 빈으로 등록해주기만 하면 된다.

```java
@Configuration
public class WebConfig {

    @Bean
    public LocaleResolver localeResolver() {
        CookieLocaleResolver resolver = new CookieLocaleResolver("lang");
        resolver.setDefaultLocale(Locale.KOREA); // 기본 로케일 설정
        // resolver.setCookieMaxAge(60 * 60 * 24 * 365); // 쿠키 유효기간 설정
        return resolver;
    }
}
```

이제 컨트롤러에서 언어 변경 요청을 받아 LocaleResolver의 setLocale() 메서드를 호출하면,

CookieLocaleResolver가 lang이라는 이름의 쿠키에 사용자가 선택한 로케일 정보를 저장하고,

이후의 모든 요청에서는 해당 쿠키 값을 기반으로 언어를 결정하게 된다.
