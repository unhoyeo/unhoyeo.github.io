SSR과 CSR은 웹 애플리케이션에서 HTML 콘텐츠를 언제, 어디서 생성할 것인가에 대한 렌더링 전략이다.

---

## SSR (Server-Side Rendering)

- **서버에서 HTML을 완성**하여 클라이언트로 전달하는 방식이다.
- 브라우저는 서버로부터 완성된 HTML을 받아 바로 렌더링한다.
- 대표적인 예: JSP, Thymeleaf

## 동작 방식

1. 사용자가 URL 접근
2. 서버는 라우팅에 따라 데이터 조회 후 HTML 완성
3. 클라이언트에 완성된 HTML 반환 → 즉시 화면 표시

## 장점

- 첫 페이지 로딩 속도가 빠름
- 검색 엔진 최적화(SEO)에 유리함 → HTML이 바로 존재하므로 검색 엔진이 인식 가능
- JS 비활성화 환경에서도 작동 가능

## 단점

- 서버 리소스를 많이 소모함 → 라우팅 시마다 HTML 새로 생성하므로
- 페이지 간 전환 시 매번 서버 요청 발생 가능
- 클라이언트 상태 기반 UI 구성에 제약이 있다

> **라우팅?**
> 사용자가 요청한 URL 경로(path)에 따라, 어떤 페이지나 컴포넌트를 보여줄지를 결정하는 행위
> 예: /home → 홈 페이지, /products/123 → 상품 123 상세 페이지

---

## CSR (Client-Side Rendering)

- 클라이언트 측에서 자바스크립트를 통해 HTML을 **동적으로 생성**하는 방식이다.
- 초기 요청 시 최소한의 HTML과 자바스크립트 파일을 받아오고,
- 이후 자바스크립트가 실행되며 필요한 데이터를 API로 받아와 화면을 구성한다.
- 대표적인 예: React, Vue 등 SPA 프레임워크

## 동작 방식

1. 사용자가 URL 접근
2. 서버는 기본 HTML 파일과 JS 번들 파일을 응답
3. 브라우저는 JS 파일을 다운받고 실행
4. JS가 API를 통해 데이터를 가져오고 DOM을 구성

## 장점

- 한 번 페이지 로딩 후 빠른 라우팅 (SPA의 장점)
- 사용자 상호작용이 많을 때 빠르고 부드러운 경험 제공
- 클라이언트 상태 기반 복잡한 UI 구성 가능
- 백엔드와 프론트엔드 완전히 분리 가능

## 단점

- 초기 로딩이 느림 (JS가 실행되어야 화면 표시됨)
- 검색 엔진 최적화(SEO)에 불리함 → 크롤러가 JS를 제대로 실행하지 못하면 콘텐츠 인식 불가
- JS가 비활성화된 환경에서는 작동 불가

> **SPA?**
> Single Page Application → 단 하나의 HTML 페이지로 구성된 웹 애플리케이션최초 로딩 시 전체 구조와 자바스크립트를 불러오고, 이후에는 서버에 새로 요청하지 않고 자바스크립트로 동적으로 페이지를 바꿈
>
> 브라우저 주소(URL)는 계속 바뀌지만,
> 실제로 HTML 페이지 전체를 새로 요청하지는 않고,
> 자바스크립트가 필요한 데이터만 서버에 요청하고,
> 화면을 클라이언트에서 렌더링

> **DOM?**
> Document Object Model → 웹 페이지의 구조(HTML 문서)를 객체처럼 표현한 계층적 구조웹 브라우저가 HTML을 해석해서 메모리상에 구성하는 트리 형태의 자료구조
>
> Document
>  └── html
>  └── body
>  ├── h1 ("안녕하세요")
>  └── p ("설명 문구")

## 비교

|  |  |  |
| --- | --- | --- |
| **항목** | **SSR** | **CSR** |
| HTML 생성 위치 | 서버 | 클라이언트 (브라우저) |
| 초기 로딩 속도 | 빠름 | 느림 |
| 라우팅 속도 | 느림 (서버 요청 필요) | 빠름 (SPA) |
| SEO 적합성 | 좋음 | 나쁨 |
| JS 의존성 | 낮음 | 높음 |
| 서버 부하 | 높음 (요청마다 렌더링) | 낮음 |

---

## 현대 프레임워크에서의 혼합 전략

- Next.js, Nuxt.js 등은 CSR과 SSR을 함께 사용하는 하이브리드 방식을 지원한다.
- 예를 들어, 메인 페이지는 SSR로 처리하고, 내부 페이지나 비동기 요청은 CSR로 처리한다.
- 이를 통해 초기 속도, SEO, 사용자 경험을 모두 일정 수준 유지할 수 있다.
