HTTP에서 클라이언트가 서버로 데이터를 전송하는 방법은 **데이터 전달 위치**에 따라 크게 **'URL을 통한 방법'**과 '**메시지 본문을 통한 방법'** 2가지가 있다.

- **URL을 통해 전달:** Query Parameter, Path Variable
- **메시지 본문을 통해 전달:** application/x-www-form-urlencoded, multipart/form-data, application/json

---

## ✅ 1. 쿼리 파라미터 (Query Parameter)

- 데이터를 ?key=value 형식으로 **URL에 포함**하여 전송 → **URL 인코딩 필수**
- 주로 **GET**, **DELETE** 요청에서 사용

**? 1.1. GET에서 쿼리 파라미터를 사용하는 이유?**

- GET은 **리소스를 조회하기 위한 요청**이다.
- 클라이언트가 서버에 특정한 데이터를 요청할 때, **필터링, 정렬, 페이징** 등 특정조건을 전달하기 위해 쿼리 파라미터를 사용한다.
- **요청 본문이 없어야 한다는 명확한 표준은 없지만**, 실제로 대부분의 서버와 브라우저는 GET 요청에 **본문을 허용하지 않는다.**
- 따라서, **모든 요청 데이터는 URI에 포함되어야 하며**, 그 구조가 쿼리 파라미터로 정해져 있다.

## 예시

```java
GET /products?category=shoes&sort=price_desc&page=2
```

**? 1.2. DELETE에서 쿼리 파라미터를 사용하는 이유?**

- DELETE는 **리소스를 제거하기 위한 요청**이다.
- 원래 DELETE는 **명확한 자원 식별이 필수**다.
- 일반적으로는 /resource/{id}와 같이 **경로 변수(Path Variable)**를 통해 삭제할 리소스를 명확히 지정한다.
- 그러나, **단일 ID로 자원을 표현하기 어려운 경우(조건 기반 삭제 등)**에는 쿼리 파라미터가 유용하다.
- DELETE 역시 요청 본문을 허용하긴 한다.
- 하지만 브라우저나 일부 프록시, API Gateway가 **본문이 있는 DELETE를 지원하지 않는 경우**가 많다.
- 따라서 **쿼리 파라미터 방식이 호환성 측면에서 더 안전하다.**

## 예시

```java
DELETE /logs?type=debug&before=2024-01-01
```

> API Gateway는 마이크로서비스 아키텍처나 클라우드 기반 시스템에서 클라이언트 요청을 **단일 진입점(Entry Point)**으로 받아, 내부의 여러 서비스로 **적절히 라우팅**하고 **공통 기능을 중앙에서 처리**하는 프록시 서버

## ✅ 2. 경로 변수 (Path Variable)

- **리소스 식별자(ID)**를 **URL 경로 자체**에 포함하여 전송 → **URL 인코딩 필수**
- **RESTful** 설계에서 자주 사용
- 필터링 목적의 쿼리 파라미터에 비해, 경로 변수는 **식별 목적**으로 사용

## 예시

```java
GET /users/123   // 123이라는 값이 리소스 식별자 역할
```

```html
GET /static/star.jpg
```

## ✅ 3. application/x-www-form-urlencoded

- HTML에서 주로 **폼(form)** 데이터를 서버로 전송할 때 사용되는 **HTTP 요청 본문 인코딩 방식**
- 데이터를 **key1=value1&key2=value2** 형식으로 요청 본문에 담아 전송
- **URL 인코딩**(percent-encoding) 방식으로 인코딩하되, **"공백은 +로"**
- 주로 **POST, PUT, PATCH** 요청에서 사용
- 단, HTML &lt;form> 태그의 method 속성은 **GET, POST만 가능**

## 예시

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 29

username=admin&password=1234
```

> Spring에서는 @RequestParam, @ModelAttribute로 처리,
> 중복 키(key=value1&key=value2)는 List, 배열, MultiValueMap으로 받을 수 있음

## 장점

- **간결하고 단순**: 모든 값이 문자열 기반이라 파싱이 용이함
- **HTML 폼과 연계 우수**: 기본 submit 방식과 완벽 호환
- **표준화 및 폭넓은 지원**: 모든 브라우저, 서버 프레임워크가 지원

## 단점

- **복잡한 데이터 구조 부적합**: 중첩 구조, 배열, 파일 등 표현 불가
- **바이너리 데이터 미지원**: 이미지, 파일은 multipart/form-data 필요
- **JSON처럼 구조화된 표현 불가**: 객체/리스트 직렬화 어려움

## ✅ 4. multipart/form-data

- HTTP 요청에서 **여러 개의 데이터를 각기 다른 "파트"로 나누어 전송**하는 방식
- 특히 **파일 업로드** 또는 **복합 데이터 전송**에 필수적으로 사용됨
- application/x-www-form-urlencoded로는 불가능한 **이진(binary) 데이터 전송** 지원
- 각 파트는 하나의 폼 필드에 대응하며, 텍스트 또는 파일 등 **다양한 데이터 형식 포함 가능**
- 각 파트는 **boundary**라는 문자열로 구분하며, **개별 헤더/바디 구조**
- 파일은 인코딩 없이 그대로 전송됨 (바이너리)

## 예시

```http
POST /upload HTTP/1.1
Host: example.com
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Length: 357

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="title"

myphoto
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="image"; filename="dog.jpg"
Content-Type: image/jpeg

(binary image data...)
------WebKitFormBoundary7MA4YWxkTrZu0gW--
```

> Content-Disposition: 폼 필드 이름 및 파일 이름 지정

> Spring에서는 MultipartFile로 받음

## 브라우저 전송 예시

```html
<form action="/upload" method="post" enctype="multipart/form-data">
  <input type="text" name="username" />
  <input type="file" name="profileImage" />
  <button type="submit">Submit</button>
</form>
```

- **enctype="multipart/form-data"**를 지정해야 파일 업로드 가능
- 지정하지 않으면, 기본 application/x-www-form-urlencoded로 처리됨 (파일 업로드 불가)

## 보안 고려사항

|  |  |
| --- | --- |
| **위험** | **대응 방안** |
| 악성 확장자 업로드 | 업로드 시 파일 확장자, Content-Type 검사 |
| 대용량 공격 (DoS) | max-file-size 제한 설정 |
| 경로 조작 (../ 등) | 서버 측 저장 경로와 이름 직접 설정 |
| 디스크 공간 고갈 | 업로드 후 불필요한 파일 즉시 삭제 |

## REST API에서의 사용

|  |  |
| --- | --- |
| **상황** | **권장 방식** |
| JSON + 파일 동시 전송 | multipart/form-data + JSON 문자열 필드 |
| JSON 전용 API | application/json + @RequestBody |
| 대용량 파일 API | multipart/form-data + 파일 스트림 처리 |

> Spring에서는 JSON 파트를 수동으로 역직렬화하여 DTO로 매핑해야 하는 경우도 존재 (@RequestPart 활용)

## ✅ 5. application/json

- HTTP 요청 또는 응답에서 **JSON** 형식의 데이터를 전송할 때 사용하는 **표준 Content-Type**
- REST API와 같은 현대 웹 시스템에서 **가장 널리 사용되는 데이터 교환 형식**
- **계층적(중첩) 구조 데이터 표현** 가능
- XML 대비 가볍고 짧음
- 다양한 프로그래밍 언어에서 **직렬화/역직렬화 처리 용이**
- HTML form의 경우, 자바스크립트를 통한 통신에 사용 (AJAX)

## 예시 1: 요청(Request)

```http
POST /users HTTP/1.1
Content-Type: application/json

{
  "name": "홍길동",
  "age": 30,
  "email": "gildong@example.com"
}
```

## 예시 2: 응답(Response)

```java
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 1001,
  "name": "홍길동",
  "roles": ["USER", "ADMIN"],
  "address": {
    "city": "서울",
    "zip": "12345"
  }
}
```

> 데이터 구조: 숫자, 문자열, 배열, 객체(JSON Object)

> Spring에서는 @RequestBody, @ResponseBody, Jackson으로 처리

## 주의사항

|  |  |
| --- | --- |
| 파일 전송 | 불가 (파일은 multipart/form-data 사용) |
| GET + JSON | HTTP 표준상 GET에 바디 금지 → URL 쿼리로 대체해야 함 |
| XSS 공격 | JSON 출력 시 이스케이프 필요 (<, >, &) |
| CSRF 공격 | 쿠키 인증 기반일 경우 CSRF 대비 필요 |
| 데이터 검증 | DTO 검증 어노테이션 사용 (@Valid) |

## Content-Type vs Accept

|  |  |  |
| --- | --- | --- |
| **헤더** | **의미** | **예시** |
| Content-Type | **요청 바디 형식** 지정 | Content-Type: application/json |
| Accept | **응답 기대 형식** 지정 | Accept: application/json |

> **참고하면 좋은 URI 설계 개념**

## 문서 (document)

- 단일 개념 (파일 하나, 객체 인스턴스, 데이터베이스의 row)
- 예: /users/123, /files/star.jpg

## 컬렉션 (collection) - POST 기반 등록

- **서버가 관리**하는 리소스 디렉토리 (예: 회원 관리)
- 클라이언트는 등록될 리소스의 URI를 **모른다. (POST /users)**
- 서버가 등록된 리소스의 URI를 생성하고 관리한다. (201 Created, Location: /users/123)
- 예: /users

## 스토어 (store) - PUT 기반 등록

- **클라이언트가 관리**하는 리소스 저장소(예: 정적 컨텐츠, 원격 파일 관리)
- 클라이언트가 등록될 리소스의 URI를 **알고 관리한다. (PUT /files/star.jpg)**
- 클라이언트가 직접 리소스의 **URI를 지정**한다.
- 예: /files

## 컨트롤 URI

- 문서, 컬렉션, 스토어로 해결하기 어려운 프로세스를 실행할 때
- HTTP 메서드로 해결하기 애매할 때
- GET, POST만 지원하는 HTML FORM의 제약을 해결할 때
- **동사로 된 리소스 경로**를 사용한다.
- 예: /orders/123/start-delivery

## URL 인코딩 (Percent-Encoding)

URL 인코딩은 **URL 내에서 허용되지 않거나 특별한 의미를 갖는 문자를 안전하게 전송하기 위해 인코딩하는 방식**이다.

공식 명칭은 **Percent-Encoding**이며, [RFC 3986](https://datatracker.ietf.org/doc/html/rfc3986)에서 정의되어 있다.

URL은 특정한 문자만 허용한다. 예를 들어 **공백, 한글, 특수문자, 예약어**는 URL에서 사용할 수 없기 때문에 인코딩해야 한다.

---

## ✅ 허용 문자 (Unreserved Characters)

아래 문자는 URL 내에서 **인코딩 없이 사용 가능**하다.

```java
알파벳 대/소문자: A-Z, a-z
숫자: 0-9
기호: - _ . ~
```

## 예약 문자 (Reserved Characters)

아래 문자는 **특별한 의미**를 가지므로 **인코딩해야 한다.**

|  |  |
| --- | --- |
| : | 프로토콜 구분 (https:) |
| / | 경로 구분 |
| ? | 쿼리 시작 |
| & | 파라미터 구분 |
| = | 파라미터 키-값 구분 |
| # | 프래그먼트 시작 |
| + | 공백 대체 문자로 사용되기도 함 (주의) |

이 외에도 **공백, %, 한글** 등은 인코딩 필수다.

---

## 인코딩 방식

- 인코딩 대상 문자를 **UTF-8**로 바이트화한 뒤,
- 각 바이트를 **16진수 2자리로 표현**하고, 그 앞에 %를 붙인다.

## 예시

|  |  |  |
| --- | --- | --- |
| **문자** | **UTF-8 (16진수)** | **URL 인코딩 결과** |
| 공백 | 0x20 | %20 또는 + |
| 한글 ‘가’ | EA B0 80 | %EA%B0%80 |
| & | 26 | %26 |
| = | 3D | %3D |
| + | 2B | %2B |

## ⚠️ 공백 처리 주의

|  |  |
| --- | --- |
| **일반 URL 인코딩 (RFC 3986)** | %20 |
| **application/x-www-form-urlencoded 인코딩** | + |

→ **HTML form** 또는 **form-like** 전송에서는 **공백 = +**

## URL 인코딩과 Content-Type 연관성

|  |  |
| --- | --- |
| **Content-Type** | **URL 인코딩 여부** |
| application/x-www-form-urlencoded | O (공백은 +) |
| multipart/form-data | X (필드별 boundary 사용) |
| application/json | X (JSON 자체 인코딩) |
