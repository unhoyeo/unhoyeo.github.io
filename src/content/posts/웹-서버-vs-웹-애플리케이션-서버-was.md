## 웹은 HTTP 기반의 통신

웹은 클라이언트(브라우저)와 서버가 HTTP 프로토콜을 통해 데이터를 주고받는 구조다.

사용자는 브라우저를 통해 HTML, CSS, JS 등을 요청하고, 서버는 그에 응답한다.

---

## 웹 서버 (Web Server)

- HTTP 요청을 받아서 **정적 리소스를 응답**하는 서버
- 정적 리소스: 고정된 파일 (HTML, CSS, JS, 이미지 등)
- 애플리케이션 로직을 처리하지 않고, 정적인 파일을 그대로 제공함

## 대표 웹 서버

- NGINX
- Apache HTTP Server

---

## WAS (Web Application Server)

- HTTP 요청을 받아서 **비즈니스 로직(애플리케이션 코드)을 실행**하는 서버
- HTML을 동적으로 생성하거나, 데이터베이스에 접근, 사용자 인증 등
- 웹 서버의 기능도 포함하고 있음

## 동작 예시

- 사용자가 로그인 시도를 하면, WAS는 로그인 로직을 수행하고 결과를 HTML 또는 JSON으로 응답

## 자바 기반 WAS

- Tomcat: 서블릿 컨테이너
- Jetty
- Undertow

## 동작하는 기술

- 서블릿(Servlet), JSP, 스프링 MVC 등은 모두 WAS 안에서 실행됨

---

## 웹 서버 vs WAS 차이

|  |  |  |
| --- | --- | --- |
| **구분** | **웹 서버** | **WAS** |
| 주된 역할 | 정적 리소스만 제공 | 동적 리소스 처리 (애플리케이션 로직 수행) |
| 실행 대상 | HTML, CSS, JS, 이미지 등 | 자바 코드, 서블릿, JSP, 스프링 컨트롤러 등 |
| 처리 방식 | 파일 그대로 반환 | 요청을 처리하여 결과를 반환 |
| 특징 | 빠르고 가벼움 | 무겁고 처리 비용 큼 |
| 예시 | NGINX, Apache | Tomcat, Jetty, Undertow |

> 사실 두 용어와 경계가 모호하다.
> 자바는 "서블릿 컨테이너 기능"이 있다면 WAS로 분류 (하지만 서블릿 없이 자바 코드를 실행하는 서버 프레임워크도 있음)
> 결론: WAS는 애플리케이션 코드를 실행하는데 특화

## 웹 시스템 구성 방식

## 최소 구성: WAS + DB

- 모든 요청을 WAS가 받아서 처리
- 작은 규모 시스템에서는 가능
- 문제점:
  - WAS가 너무 많은 역할을 담당 → 서버 과부화
  - 정적 리소스도 WAS가 처리 → 성능 낭비
  - WAS가 다운되면 오류 화면도 못 띄움

> 가장 비싼 애플리케이션 로직이 값싼 정적 리소스 때문에 수행이 어려울 수 있음

## 확장 구성: 웹 서버 + WAS + DB

- **정적 리소스**는 웹 서버에서 빠르게 처리
- **동적 요청**은 웹 서버가 WAS로 전달
- 이점:
  - WAS는 오직 비즈니스 로직에 집중 → 리소스 효율
  - 장애 분산: WAS가 죽어도 웹 서버가 오류 페이지 제공 가능
  - 서버 확장 유연: 정적 요청 증가 시 웹 서버만 증설, 동적 요청 증가 시 WAS만 증설

> 정적 리소스를 캐시할 수 있는 서버(CDN)를 중간에 둘 수도 있다.

## CDN (Content Delivery Network)

- 정적 리소스를 캐싱하는 전 세계 분산 서버
- 웹 서버 앞에 위치하여, 전 세계 사용자에게 빠르게 정적 리소스 제공
- 정적 리소스 요청의 상당 부분을 CDN이 처리 → 웹 서버, WAS의 부하 감소

---

## 결론

- 웹 서버는 정적 파일 전용
- WAS는 동적 로직 전용
- 이 둘을 분리하면:
  - 성능 향상
  - 안정성 증가
  - 운영 효율성 향상
- 대규모 시스템은 반드시 이 구조를 따른다.
