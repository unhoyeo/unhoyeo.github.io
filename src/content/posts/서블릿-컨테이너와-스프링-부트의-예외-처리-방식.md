웹 애플리케이션에서 예외 처리는 서비스의 안정성과 사용자 경험을 결정하는 매우 중요한 요소다.

사용자는 서버의 내부 오류(예: 하얀색 오류 화면)를 보고 싶어 하지 않으며, 개발자는 오류의 원인을 명확하게 파악하고 싶어 한다.

우선 스프링이 제공하는 편리한 기능을 다루기 전에, 그 근간이 되는 **서블릿 컨테이너의 예외 처리 방식**을 알아보자.

> WAS가 제공하는 기본 오류 페이지를 보려면 스프링이 제공하는 기본 오류 페이지인 Whitelabel Error Page를 비활성화해야 한다.
> application.properties 파일에 server.error.whitelabel.enabled=false 옵션을 추가하면 된다.

---

## 서블릿 컨테이너의 예외 처리 방식

서블릿은 두 가지 방식으로 예외 상황을 인지하고 처리한다.

1. **예외(Exception) 전파**
2. **response.sendError(statusCode, message) 호출**

---

## 예외(Exception) 전파

컨트롤러에서 발생한 예외가 try-catch로 처리되지 않고 계속해서 **상위로 전파**되면, 최종적으로 **서블릿 컨테이너**(WAS)까지 도달한다.

> **서블릿 컨테이너**(WAS)? ← 필터? ← 서블릿(DispatcherServlet)? ← 인터셉터? ← **컨트롤러**?(예외 발생!)

WAS는 이를 처리할 수 없는 <strong>서버 내부 오류(Internal Server Error)</strong>로 간주하고, 기본적으로 <strong>500</strong> 응답을 보낸다.

---

## response.sendError(statusCode, message) 호출

이 방식은 개발자가 컨트롤러 코드 내에서 **명시적으로** WAS에게 오류 상황을 알리는 방식이다.

```java
@GetMapping("/404")
public void err404(HttpServletResponse response) throws IOException {
    response.sendError(404, "404 에러 발생");
}
```

이 메서드가 호출되면 response 객체 내부에 **오류가 발생했다는 상태가 저장**된다.

WAS는 응답 전에 response 객체에 **오류 발생 상태가 있는지 확인**하여, 오류가 있다면 지정된 상태 코드에 맞는 **오류 페이지**를 보여준다.

---

## 기본 오류 페이지의 문제점

WAS가 기본으로 제공하는 오류 페이지는 **사용자 친화적이지 않으며**, 서비스의 정체성을 보여주지 못한다.

![서블릿 컨테이너와 스프링 부트의 예외 처리 방식](/images/tistory/221/img.png)

따라서 기본 오류 페이지 대신, 개발자가 직접 만든 **커스텀 오류 페이지**를 보여줘야 한다.

---

## 커스텀 오류 페이지 지정

서블릿은 특정 예외나 오류 코드에 대해 응답할 **오류 페이지 경로**를 지정하는 기능을 제공한다.

과거에는 **web.xml** 파일에 다음과 같이 오류 페이지를 등록했다.

```html
<web-app>
    <error-page>
        <error-code>404</error-code>
        <location>/error-page/404.html</location>
    </error-page>
    <error-page>
        <error-code>500</error-code>
        <location>/error-page/500.html</location>
    </error-page>
    <error-page>
        <exception-type>java.lang.RuntimeException</exception-type>
        <location>/error-page/500.html</location>
    </error-page>
</web-app>
```

스프링 부트에서는 **WebServerFactoryCustomizer**를 구현하여 이를 설정할 수 있다.

```java
@Component
public class WebServerCustomizer implements
        WebServerFactoryCustomizer<ConfigurableWebServerFactory> {

    @Override
    public void customize(ConfigurableWebServerFactory factory) {
        // 404 오류 발생 시 /error-page/404 경로로 요청
        ErrorPage errorPage404 = new ErrorPage(
                HttpStatus.NOT_FOUND, // status
                "/error-page/404"     // path
        );

        // 500 오류 발생 시 /error-page/500 경로로 요청
        ErrorPage errorPage500 = new ErrorPage(
                HttpStatus.INTERNAL_SERVER_ERROR,
                "/error-page/500"
        );

        // RuntimeException(또는 그 자식 타입) 발생 시 /error-page/500 경로로 요청
        ErrorPage errorPageEx = new ErrorPage(
                RuntimeException.class, // exception
                "/error-page/500"       // path
        );

        factory.addErrorPages(errorPage404, errorPage500, errorPageEx);
    }
}
```

- 위 클래스에 등록한 오류가 발생하면, 서블릿 컨테이너는 해당 오류에 **지정된 경로로 다시 요청**을 보내게 된다.
  - 이때 WAS는 해당 요청의 **request 객체**에 발생한 예외, 상태 코드 등의 **추가적인 오류 정보**를 attribute에 담아서 넘겨준다.
- 따라서 **컨트롤러에서 해당 요청을 받아** 적절한 에러 페이지를 보여주면 된다.

```java
@Controller
public class ErrorPageController {

    @RequestMapping("/error-page/404")
    public String errorPage404(HttpServletRequest request) {
        // WAS가 에러 처리 요청을 보내면서 request 객체에 담은 정보들
        request.getAttribute(RequestDispatcher.ERROR_EXCEPTION);      // 예외
        request.getAttribute(RequestDispatcher.ERROR_EXCEPTION_TYPE); // 예외 타입
        request.getAttribute(RequestDispatcher.ERROR_MESSAGE);        // 오류 메시지
        request.getAttribute(RequestDispatcher.ERROR_REQUEST_URI);    // 클라이언트 요청 URI
        request.getAttribute(RequestDispatcher.ERROR_SERVLET_NAME);   // 오류가 발생한 서블릿 이름
        request.getAttribute(RequestDispatcher.ERROR_STATUS_CODE);    // HTTP 상태 코드

        // 커스텀 오류 페이지(error-page/404.html)를 보여줌
        return "error-page/404";
    }

    @RequestMapping("/error-page/500")
    public String errorPage500(HttpServletRequest request) {
        return "error-page/500";
    }
}
```

## 오류 페이지 작동 원리

1. 컨트롤러에서 예외가 발생하거나, sendError()가 호출되어 **WAS에 오류가 전달됨**
2. WAS는 **설정된 오류 페이지가 있는지** 확인함 (예: 500 오류 → /error-page/500)
3. WAS는 오류 페이지를 클라이언트에게 보여주기 위해, **지정된 경로**(/error-page/500)로 서버 내부에서 **새로운 요청**을 보냄
4. 이 새로운 요청은 **필터 → 서블릿 → 인터셉터 → 컨트롤러**를 모두 다시 거쳐서 처리됨

> 서블릿 컨테이너(WAS)? ← 필터? ← 서블릿(DispatcherServlet)? ← 인터셉터? ← 컨트롤러?(예외 발생!)
>  ↓
> **(다시 /error-page/500 요청)** → 필터 → 서블릿 → 인터셉터 → 컨트롤러 → **View?(에러 페이지 렌더링)**

즉, 클라이언트는 한 번만 요청했지만, 서버 내부에서는 **(1) 원래 요청 → (2) 오류 페이지 요청** 두 단계가 진행된다.

---

## 문제점: 필터와 인터셉터의 중복 호출

- 오류 페이지를 보여주기 위해 내부적으로 **새로운 요청**이 발생하면서, **필터와 인터셉터가 중복으로 호출되는 문제**가 발생한다.
- 따라서 해당 요청이 클라이언트가 보낸 **원래 요청**인지, 오류 페이지를 출력하기 위한 **내부 요청**인지 **구분할 수 있어야 한다.**
- **필터**의 경우 **DispatcherType**으로 해결 가능
- **인터셉터**의 경우 **excludePathPatterns**로 해결 가능

---

## 필터 중복 호출 해결 – DispatcherType

요청의 타입을 구분하기 위해 서블릿은 **DispatcherType**이라는 개념을 제공한다.

```java
public enum DispatcherType {

    // 다른 서블릿이나 JSP 호출 시 (RequestDispatcher.forward())
    FORWARD,

    // 서블릿에서 다른 서블릿이나 JSP의 결과를 포함 시 (RequestDispatcher.include())
    INCLUDE,

    // 일반적인 클라이언트 요청
    REQUEST,

    // 서블릿 비동기 호출 시 (AsyncContext.dispatch(), AsyncContext.addListener() 메서드)
    ASYNC,

    // 컨테이너가 오류 페이지 처리 요청 시
    ERROR
}
```

- 클라이언트로부터 온 최초의 정상 요청: **DispatcherType.REQUEST**
- 오류 페이지 출력을 위한 서버 내부 요청: **DispatcherType.ERROR**

서블릿 필터의 경우, 등록할 때 <strong>setDispatcherTypes()</strong>를 사용하여 <strong>어떤 타입의 요청에 필터를 적용할지</strong> 지정할 수 있다.

```java
@Configuration
public class WebConfig {

    @Bean
    public FilterRegistrationBean<LogFilter> logFilter() {
        FilterRegistrationBean<LogFilter> registrationBean = new FilterRegistrationBean<>();
        registrationBean.setFilter(new LogFilter());
        registrationBean.setOrder(1);
        registrationBean.addUrlPatterns("/*");

        // 필터의 DispatcherType 지정
        registrationBean.setDispatcherTypes(
                DispatcherType.REQUEST,
                DispatcherType.ERROR
        );

        return registrationBean;
    }
}
```

기본값은 **REQUEST**이므로, 별도 설정이 없다면 **오류 페이지 요청 시에는 필터가 호출되지 않는다.**

## 인터셉터 중복 호출 해결 – excludePathPatterns

서블릿 필터는 적용할 DispatcherType을 지정할 수 있었지만, 인터셉터는 **DispatcherType과 상관없이 항상 호출된다.**

대신, <strong>excludePathPatterns</strong>를 사용하여 <strong>오류 페이지 경로(/error-page/\*\*)</strong>를 제외함으로써 간단하게 해결할 수 있다.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LogInterceptor())
                .order(1)
                .addPathPatterns("/**")
                .excludePathPatterns(
                        "/css/**", "/*.ico", "/error",
                        "/error-page/**" // 오류 페이지 경로 제외
                );
    }
}
```

## 스프링 부트의 예외 처리 방식

스프링 부트는 지금까지의 모든 복잡한 과정(WebServerCustomizer 설정, 오류 처리용 컨트롤러 생성 등)을 모두 자동화했다.

1. **ErrorPage 자동 등록**
   - 스프링 부트는 **ErrorMvcAutoConfiguration** 클래스를 통해 ErrorPage를 자동으로 등록한다.
   - 이때 모든 오류 처리 요청의 경로를 **/error**로 지정한다.
2. **BasicErrorController 자동 등록**
   - **/error** 경로의 요청을 처리하는 컨트롤러를 자동으로 빈으로 등록한다.
   - BasicErrorController는 **timestamp, exception, trace, path** 등 유용한 오류 정보를 **모델**에 담아 뷰에 전달한다.
   - ⚠️ 단, 보안상의 이유로 실제 운영 환경에서는 application.properties의 server.error.include-\* 옵션을 통해 민감한 정보(예: stacktrace)가 사용자에게 노출되지 않도록 제어해야 한다.
3. **규칙에 따른 뷰(View) 제공**
   - 개발자는 그저 정해진 위치에 **오류 페이지 파일**만 만들어 두면 된다.
   - 그러면 BasicErrorController가 알아서 HTTP 상태 코드에 맞는 파일을 찾아 렌더링한다.

## BasicErrorController의 뷰 선택 우선순위

아래 우선순위에 따라 해당 경로에 <strong>"상태 코드"</strong>를 이름으로 하는 HTML 파일을 만들면 된다.

1. **뷰 템플릿 (resources/templates/error/)**
   1. **구체적인 상태 코드**: 500.html, 404.html
   2. **상태 코드 시리즈**: 5xx.html, 4xx.html (해당 계열의 오류 처리)
2. **정적 리소스 (resources/static/error/)**
   1. **구체적인 상태 코드**: 500.html, 404.html
   2. **상태 코드 시리즈**: 5xx.html, 4xx.html (해당 계열의 오류 처리)
3. **기본 오류 페이지 (resources/templates/error.html)**
   - 위에서 해당하는 페이지가 없을 때 기본으로 사용

> 뷰 템플릿 > 정적 리소스 (뷰 템플릿이 정적 리소스보다 우선순위가 높음)
> 404 > 4xx (구체적인 상태 코드일수록 우선순위가 높음)
