## Part 1. 개요 — 로그에서 요청 하나를 찾는 문제

안녕하세요, 백엔드를 공부하고 있는 여운호입니다. 주문 API를 만들면서 로깅을 다루던 중에 겪은 일을 정리했습니다.

로그를 남기는 것 자체는 어렵지 않았습니다. 문제는 **남긴 로그에서 필요한 것을 찾는 일**이었습니다. 요청이 하나씩 들어올 때는 아무 문제가 없다가, 동시에 여러 건이 들어오는 상황을 가정하니 이야기가 달라졌습니다.

이번 글에서는 요청 추적을 위해 MDC를 도입한 과정과, **도입한 뒤에 만난 세 가지 문제**를 어떻게 재현하고 해결했는지를 풀어 보려 합니다. 세 문제 모두 에러가 나지 않고 평소에는 티도 나지 않는 종류였습니다. 직접 코드를 되돌려 돌려보기 전까지는 로그만 봐서 알 수 없었습니다.

다루는 대상은 아래와 같은 주문 흐름입니다.

```text
HTTP 요청 → 재고 차감 → 결제 → [트랜잭션 커밋] → 알림 발송(@Async)
└──────────── 톰캣 스레드 ────────────┘            └─ 알림 전용 스레드
```

그림 1. 주문 하나가 지나는 구간. 마지막 알림만 다른 스레드에서 실행된다.

## Part 2. MDC 도입까지

### 2.1 동시 요청에서 흐름이 끊기는 지점

주문 두 건을 동시에 보내고 로그를 봤습니다. 하나는 결제 성공, 하나는 결제 거절입니다.

```text
INFO [http-nio-8080-exec-2] OrderService        - Order created: productId=2, quantity=1, totalPrice=489000.00
INFO [http-nio-8080-exec-3] OrderService        - Order created: productId=1, quantity=2, totalPrice=258000.00
INFO [http-nio-8080-exec-2] FakePaymentClient   - Fake payment requested: scenario=FAILURE, amount=489000.00
INFO [http-nio-8080-exec-3] FakePaymentClient   - Fake payment requested: scenario=SUCCESS, amount=258000.00
WARN [http-nio-8080-exec-2] OrderService        - Payment failed: reason=결제가 거절되었습니다.
INFO [http-nio-8080-exec-3] OrderService        - Payment approved: transactionId=fake-43983592-...
INFO [notification-1]       NotificationService - Order completion notification sent: orderId=1
```

로그는 한 줄도 빠지지 않았습니다. 그런데 **"결제가 거절된 그 요청"의 전체 흐름을 뽑아낼 수가 없습니다.** 막히는 지점이 두 군데였습니다.

첫째, `Fake payment requested` 줄에는 주문 번호가 없습니다. 금액만 있으니 같은 금액의 주문이 둘이면 구분할 방법이 사라집니다.

둘째, 마지막 줄은 **아예 다른 스레드**입니다. 위 요청 중 어느 것에서 나온 건지 이어 붙일 방법이 없습니다.

여기서 `[exec-2]` 같은 스레드 이름으로 묶으면 되지 않겠냐는 생각이 먼저 들었습니다. 하지만 두 가지 이유로 안 됩니다. 톰캣은 스레드를 **재사용**하므로 `exec-2`는 조금 뒤 다른 사용자의 요청을 처리합니다. 그리고 비동기 알림은 **애초에 다른 스레드**라 그 결과에서 빠져 버립니다.

정리하면 스레드 이름은 **누가 처리했는가**이지 **무슨 요청인가**가 아닙니다. 일꾼과 요청이 1:1이 아니기 때문에, 요청 자체에 식별자를 붙여야 합니다.

### 2.2 첫 번째 시도 — 파라미터 전달의 한계

가장 먼저 떠오른 방법은 주문 번호를 인자로 넘기는 것이었습니다. 결제 클라이언트가 모르니 아는 쪽에서 알려 주면 되니까요.

돌려 보니 잘 됐습니다. 그런데 두 가지가 걸렸습니다.

첫째, **결제 클라이언트는 주문 번호로 아무 일도 하지 않습니다.** 오직 로그에 찍으려고 받습니다. 지금은 계층이 몇 개 안 되지만, 재고·알림까지 늘어나면 로그 한 줄 때문에 모든 메서드 시그니처에 주문 번호가 따라다니게 됩니다.

둘째, 이게 더 결정적이었는데, **제가 짜지 않은 코드의 로그에는 붙일 방법이 없습니다.** 실제로 서버를 띄우고 첫 요청을 보냈을 때 이런 줄이 먼저 나옵니다.

```text
INFO [http-nio-8080-exec-1] [traceId= ] o.s.web.servlet.DispatcherServlet - Initializing Servlet 'dispatcherServlet'
INFO [http-nio-8080-exec-1] [traceId=3fbb2a32...] c.e.t.common.logging.TraceIdFilter - HTTP request started
```

앞줄은 스프링이 찍은 줄입니다. 서블릿 초기화는 필터 체인 바깥에서 일어나기 때문에 제 필터가 아직 실행되지 않았습니다. 장애를 분석할 때 정말 중요한 줄, 그러니까 스택트레이스나 타임아웃 같은 줄은 대개 프레임워크나 라이브러리가 찍습니다. **그 코드는 jar 안에 있으니 파라미터를 넘길 방법이 없습니다.**

### 2.3 MDC 적용과 발급 위치

로그 한 줄은 두 부분으로 나뉩니다.

```text
INFO [exec-1] [traceId=3fbb2a32] DispatcherServlet - Initializing Servlet ...
└──── 내가 정한 패턴 ────────┘ └──── 찍는 쪽이 만든 메시지 ────┘
```

그림 2. 메시지는 찍는 쪽이 만들지만, 패턴은 내가 정한다.

메시지는 손댈 수 없지만 **패턴은 `logback-spring.xml`에서 제가 정합니다.** MDC는 값을 패턴 쪽에 넣는 방법입니다. 메시지가 누구 것이든 상관없이 앞에 붙습니다.

동작 원리는 단순합니다. MDC는 **스레드마다 하나씩 딸린 Map**입니다.

```java
MDC.put("traceId", traceId);   // 지금 이 스레드의 Map에 저장
```

```xml
%X{traceId}                    <!-- 로그를 찍는 스레드의 Map에서 꺼내기 -->
```

둘 다 "지금 이 스레드" 기준입니다. 요청 하나는 처음부터 끝까지 같은 스레드가 처리하니, **입구에서 한 번만 넣어 두면** 그 요청이 찍는 모든 로그에 자동으로 따라붙습니다. 값을 손에서 손으로 건네는 게 아니라, 스레드에 붙여 두고 로그가 알아서 꺼내 가게 하는 방식입니다.

발급 위치는 요청이 반드시 지나가는 가장 앞 지점, 서블릿 필터로 잡았습니다. 필터는 서블릿 규격상 `DispatcherServlet`보다 먼저 실행되므로 **컨트롤러에 도달조차 못 하는 요청도** traceId를 갖게 됩니다.

여기까지가 30분이면 되는 부분이었습니다. **어려운 건 그다음이었습니다.**

## Part 3. 도입 이후에 만난 세 가지

### 3.1 재현 환경의 구성

세 문제 모두 **평소에는 티가 나지 않습니다.** 그래서 재현을 먼저 설계해야 했습니다.

각 문제마다 **브랜치를 하나씩 만들고, 정확히 한 곳만 되돌렸습니다.** 그래야 로그의 변화가 무엇 때문인지 분명해집니다.

| 브랜치 | 되돌린 곳 | 변경 규모 |
|---|---|---|
| `experiment/mdc-no-clear` | 필터의 MDC 정리 | 1개 파일, 13줄 삭제 |
| `experiment/mdc-no-async-copy` | `AsyncConfig`의 `TaskDecorator` | 1개 파일, 3줄 삭제 |
| `experiment/mdc-no-executor-restore` | `MdcTaskDecorator`의 되돌리기 | 1개 파일 |

표 1. 문제마다 브랜치를 나누고, 브랜치마다 한 곳만 바꿨다.

그리고 확인은 IntelliJ HTTP Client로 했습니다. 각 브랜치에 `.http` 파일을 함께 뒀습니다. 다시 볼 때 명령을 기억해 낼 필요가 없도록 하기 위해서입니다.

여기에 하나가 더 필요했습니다. **확률을 1로 만드는 일**입니다.

톰캣은 기본으로 스레드를 200개까지 씁니다. 요청 두 건이 서로 다른 스레드로 흩어지면 아무 일도 안 일어난 것처럼 보입니다. 그래서 재현 전용 프로파일을 만들어 스레드를 하나로 고정했습니다.

```yaml
# application-mdcleak.yml
server:
  tomcat:
    threads:
      max: 1
      min-spare: 1
```

운영에서는 스레드가 200개라 확률이 낮아 보일 뿐입니다. 트래픽이 쌓이면 결국 같은 일이 일어납니다. **확률을 1로 만들어서 볼 뿐입니다.**

### 3.2 세 가지 실패 형태

#### 형태 A — 요청 종료 후 남는 값

필터에서 값을 넣기만 하고 정리하지 않으면 어떻게 되는지 봤습니다. 요청 세 건을 보냈고, **1번만 `X-User-Id` 헤더를 보내고 2·3번은 보내지 않았습니다.**

```text
14:03:15.173 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request started
14:03:15.296 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=1 userId=user-AAAA] OrderService  - Order created
14:03:15.348 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=1 userId=user-AAAA] OrderService  - Payment approved
14:03:15.372 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request completed

14:03:34.607 INFO [http-nio-8080-exec-1] [traceId=23d28a6f... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request started
14:03:34.635 INFO [http-nio-8080-exec-1] [traceId=23d28a6f... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request completed

14:03:44.003 INFO [http-nio-8080-exec-1] [traceId=5d0cdebd... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request started
14:03:44.009 INFO [http-nio-8080-exec-1] [traceId=5d0cdebd... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request completed
```

그림 3. 2·3번 요청은 헤더를 보내지 않았는데 `user-AAAA`가 붙어 있다.

시간을 보시면 `14:03:15` → `14:03:34` → `14:03:44`입니다. **19초, 29초가 지나도 그대로입니다.** 일시적인 현상이 아니라 서버를 내릴 때까지 사라지지 않습니다.

#### 형태 B — 비동기 스레드로 넘어가지 않는 값

이번에는 스레드를 묶을 필요가 없었습니다. `@Async` 메서드는 애초에 다른 스레드가 실행하기 때문입니다. **확률이 아니라 구조입니다.**

```text
14:24:32.880 INFO [http-nio-8080-exec-1] [traceId=f028bace... orderId=1 userId=user-AAAA] OrderService        - Order created
14:24:32.936 INFO [http-nio-8080-exec-1] [traceId=f028bace... orderId=1 userId=user-AAAA] OrderService        - Payment approved
14:24:32.939 INFO [notification-1]       [traceId=           orderId=1 userId=user-AAAA] NotificationService - 주문 알림
14:24:32.949 INFO [http-nio-8080-exec-1] [traceId=f028bace... orderId=  userId=user-AAAA] TraceIdFilter       - HTTP request completed
```

그림 4. 알림 줄만 traceId가 비어 있다.

여기서 눈여겨볼 부분이 있습니다. **형태 A에서 봤던 누수는 이 실행에 없습니다.** 두 번째 요청의 `userId`는 제대로 바뀝니다. 이번에는 필터의 정리 코드를 그대로 두고 `TaskDecorator`만 뺐기 때문입니다. **두 문제는 서로 독립입니다. 하나를 고쳐도 다른 하나는 남습니다.**

#### 형태 C — 작업 종료 후 풀 스레드에 남는 값

`TaskDecorator`로 값을 복사해 오도록 고쳤습니다. 그런데 **복사한 값을 언제 치우는지**는 아직 정하지 않은 상태였습니다.

이 재현에는 조건이 하나 더 붙었습니다. HTTP 요청에서 출발한 알림은 매번 요청 스레드의 MDC를 물려받으므로, 앞 작업의 값이 남아 있어도 **곧바로 덮어써져 티가 나지 않습니다.** 남아 있는 걸 보려면 **덮어쓸 값이 없는 작업**이 같은 스레드를 써야 합니다.

그래서 실패한 알림을 다시 보내는 **재시도 배치**를 넣었습니다. 스케줄러가 부르므로 호출 시점에 MDC가 비어 있습니다. 그리고 알림 스레드풀도 하나로 고정했습니다.

서버를 띄우고 **주문을 한 건만** 보냈습니다. 배치는 4초마다 알아서 돕니다.

```text
14:36:11.570 INFO [notification-1] [traceId=           orderId=  userId=]          NotificationService - batch-retry
14:36:15.577 INFO [notification-1] [traceId=           orderId=  userId=]          NotificationService - batch-retry

14:36:18.840 INFO [http-nio-8080-exec-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] TraceIdFilter       - HTTP request started
14:36:18.931 INFO [http-nio-8080-exec-1] [traceId=3fbb2a32... orderId=1 userId=user-AAAA] OrderService        - Order created
14:36:18.991 INFO [notification-1]       [traceId=3fbb2a32... orderId=1 userId=user-AAAA] NotificationService - 주문 알림
14:36:19.014 INFO [http-nio-8080-exec-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] TraceIdFilter       - HTTP request completed

14:36:19.583 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
14:36:23.590 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
14:36:27.595 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
14:36:31.601 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
```

그림 5. 같은 실행 안에 Before와 After가 다 있다. 경계는 주문이 들어온 14:36:18이다.

주문 **전** 배치 두 건은 traceId가 비어 있습니다. 정상입니다. 주문 **후** 배치 네 건은 그 주문의 traceId를 달고 나옵니다. 배치는 그 주문과 아무 상관이 없습니다.

### 3.3 로그 판독법 — 빈칸과 채워진 칸의 차이

세 문제를 다 재현하고 나서, 세 번 모두 같은 방법으로 원인을 좁혔다는 걸 알았습니다. **무엇이 남았고 무엇이 사라졌는지를 비교하는 것**입니다.

**[ 형태 A — 덮어쓰지 않는 키만 남는 이유 ]**

```text
traceId=51dd263a...  →  traceId=23d28a6f...  →  traceId=5d0cdebd...    매번 바뀐다
userId=user-AAAA     →  userId=user-AAAA     →  userId=user-AAAA       안 바뀐다
```

필터는 요청마다 traceId를 **무조건** 새로 넣습니다. 앞 요청 값이 있어도 덮어써지니 문제가 안 보입니다. 반면 userId는 **헤더가 있을 때만** 넣습니다. 헤더가 없으면 덮어쓰지 않으니 이전 값이 살아남습니다.

정리하면 **덮어쓰지 않는 키만 샙니다.** 그래서 이 버그는 조용합니다.

**[ 형태 A — 사라진 orderId가 주는 단서 ]**

같은 줄에서 orderId는 요청이 끝날 때 없어졌습니다.

```text
[orderId=1 userId=user-AAAA] Payment approved
[orderId=  userId=user-AAAA] HTTP request completed
 ^^^^^^^^^ 사라짐            ^^^^^^^^^^^^^^^^ 남음
```

orderId는 `try-with-resources`로 감싼 `MdcScope`가 넣고 빼는 값이라 블록이 끝나면서 정상적으로 제거됐습니다. userId만 남았다는 건 **`MdcScope`는 멀쩡하고 필터가 범인**이라는 뜻입니다.

**[ 형태 B — 넣은 값과 물려받을 값의 구분 ]**

```text
[notification-1] [traceId=  orderId=1 userId=user-AAAA]
                  ^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^
                  없다      있다
```

| 값 | 누가 넣었나 | 결과 |
|---|---|---|
| `orderId`, `userId` | 리스너가 **알림 스레드 안에서** 직접 넣음 | 그 스레드에서 보인다 |
| `traceId` | 필터가 **요청 스레드에서** 넣음 | 물려받아야 하는데 못 받았다 |

표 2. 같은 줄인데 어떤 건 있고 어떤 건 없다. 누가 넣었는지가 다르다.

MDC 자체가 고장난 게 아니라 **스레드를 건너오는 통로가 없는 것**입니다.

**[ 형태 C — 복사한 쪽의 복원 누락 ]**

```text
[traceId=3fbb2a32...  orderId=  userId=user-AAAA]  batch-retry
 ^^^^^^^^ 남음        ^^^^^^^^^ 사라짐  ^^^^^^^^^ 남음
```

orderId는 리스너의 `MdcScope`가 `close()`에서 뺐으니 남지 않습니다. traceId와 userId는 `TaskDecorator`가 복사해 넣고 되돌리지 않았으니 남습니다.

세 번 모두 이 방법으로 범인을 찾았고, **세 번 모두 `MdcScope`는 결백했습니다.**

### 3.4 세 형태의 공통 원인

MDC는 `ThreadLocal` 기반입니다. **스레드마다 저장소가 따로 있고, 스레드는 요청이 끝나도 죽지 않습니다.** 이 한 문장에서 세 문제가 모두 나옵니다.

| | 스레드의 어떤 성질 | 증상 | 어느 풀 |
|---|---|---|---|
| 형태 A | 죽지 않고 **재사용된다** | 값이 **남는다** | 톰캣 스레드 |
| 형태 B | 서로 **격리돼 있다** | 값이 **안 넘어온다** | 알림 스레드 |
| 형태 C | 죽지 않고 **재사용된다** | 값이 **남는다** | 알림 스레드 |

표 3. 하나의 성질에서 나온 세 가지 증상.

격리는 버그가 아니라 **설계입니다.** 동시 요청 두 건의 traceId가 서로 안 섞인 것도 이 격리 덕분입니다. 그 장점의 대가로 비동기에서 끊깁니다.

그리고 형태 A와 C는 같은 원인이 서로 다른 스레드풀에서 나타난 것입니다. **값을 넘겨주는 문제(B)를 풀고 나면, 넘겨준 값을 치우는 문제(C)가 새로 생깁니다.**

다만 형태 C가 A보다 나쁩니다. 톰캣 스레드는 다음 요청의 필터가 traceId만큼은 덮어써 주지만, **알림 스레드에는 매 작업마다 덮어써 줄 필터가 없습니다.** 그래서 위 로그에서는 traceId와 userId가 둘 다 샜습니다.

그럼 이제 이 세 가지를 어떻게 고쳤는지 정리해 보겠습니다.

## Part 4. 해결과 검증

### 원칙 1 — 내가 넣은 값만 복원

```java
Map<String, String> previousContext = MDC.getCopyOfContextMap();   // 들어올 때 저장
try {
    MDC.put(TRACE_ID, traceId);
    filterChain.doFilter(request, response);
} finally {
    restore(previousContext);                                      // 나갈 때 복원
}
```

`MDC.clear()` 한 줄로 끝내지 않았습니다. **이 필터보다 앞서 실행된 다른 필터가 넣어 둔 값까지 지우기 때문입니다.** 내가 넣은 것만 책임지고 되돌리는 게 맞다고 판단했습니다.

`finally`인 것도 이유가 있습니다. 예외가 터지면 그 아래 줄은 실행되지 않습니다. 그리고 **예외가 터진 순간이야말로 로그를 가장 열심히 보는 때**입니다. 그때 값이 틀려 있으면 최악입니다.

### 원칙 2 — 복사 시점과 주입 시점의 분리

스프링은 작업을 스레드풀에 넘기기 직전에 끼어들 수 있는 자리를 열어 뒀습니다. `TaskDecorator`입니다.

```java
public Runnable decorate(Runnable runnable) {
    // ① 지금 실행된다. 아직 요청 스레드다.
    Map<String, String> callerContext = MDC.getCopyOfContextMap();

    return () -> {
        // ② 나중에 실행된다. 여기는 이미 알림 스레드다.
        Map<String, String> executorContext = MDC.getCopyOfContextMap();
        try {
            replaceContext(callerContext);
            runnable.run();
        } finally {
            replaceContext(executorContext);
        }
    };
}
```

헷갈리기 쉬운 부분이 여기입니다. **바깥과 안쪽이 서로 다른 스레드에서, 다른 시점에 실행됩니다.** `return () -> {...}`는 "지금 실행하라"가 아니라 "이런 작업이 있다"를 포장해 넘기는 것입니다. 안쪽은 대기줄에서 꺼내질 때 실행됩니다.

그래서 **복사는 값이 있는 바깥(①)에서, 붙여넣기는 값이 필요한 안쪽(②)에서** 해야 합니다. 복사를 안쪽에서 하면 이미 비어 있는 저장소를 복사하게 됩니다.

### 원칙 3 — 작업 종료 후 원상 복구

위 코드의 `finally`가 형태 C를 막는 부분입니다. 풀 스레드가 원래 갖고 있던 상태를 보관했다가 작업이 끝나면 되돌립니다.

여기서 흔히 저지르는 형태가 하나 있습니다. 되돌리기 없이 **호출자가 가진 키만 덮어쓰는** 방식입니다.

```java
if (callerContext != null) {
    callerContext.forEach(MDC::put);   // 기존 값을 지우지 않는다
}
```

호출자에게 MDC가 없으면 이 `if`를 그냥 건너뜁니다. 덮어쓰지도 않으니 스레드에 남아 있던 값이 그대로 살아 있습니다. 배치처럼 요청에서 오지 않은 작업이 이 경로를 타면 **앞 사용자의 traceId를 그대로 달고 나옵니다.**

이게 traceId가 아예 없는 것보다 나쁩니다. 없으면 "모른다"로 끝나지만, **틀린 값은 조사를 엉뚱한 곳으로 끌고 갑니다.** 실제로 `grep 3fbb2a32`를 하면 그 사용자가 하지도 않은 배치 작업 네 건이 딸려 나옵니다.

### 4.4 재현 코드에서 나온 오류

형태 C를 재현하면서 한 번 헛돌았습니다. 배치를 넣고 돌렸는데 로그가 이렇게 나왔습니다.

```text
14:30:13.101 INFO [scheduling-1] [traceId= orderId= userId=] NotificationService - batch-retry
```

스레드 이름이 `notification-1`이 아니라 `scheduling-1`이었습니다. 알림 스레드풀을 거치지 않았으니 아무리 돌려도 재현될 리가 없었습니다.

원인은 `@Async`의 위치였습니다. 제 코드에서 비동기 전환은 `NotificationService`가 아니라 **이벤트 리스너에서** 일어납니다. 그래서 스케줄러가 서비스를 직접 부르면 그냥 동기로 실행됩니다. 배치가 실행기에 직접 제출하도록 고치고 나서야 같은 스레드를 물려받았습니다.

**재현 코드도 틀릴 수 있다는 걸 여기서 배웠습니다.** 로그의 스레드 이름을 확인하지 않았다면 "이 문제는 실제로는 안 일어나나 보다"라고 잘못 결론 낼 뻔했습니다.

### 4.5 회귀 테스트가 잡고 있던 것

각 브랜치에서 코드를 되돌릴 때마다 테스트가 **정확히 하나씩** 빨간불이 됐습니다.

| 되돌린 것 | 실패한 테스트 |
|---|---|
| 필터의 MDC 정리 | `TraceIdFilterTest.usesIncomingTraceIdAndRestoresPreviousContext()` |
| `TaskDecorator` | `AsyncMdcIntegrationTest.configuredExecutorCopiesRequestMdcToWorkerThread()` |
| `TaskDecorator`의 되돌리기 | `MdcTaskDecoratorTest.copiesCallerContextAndRestoresExecutorContext()` |

표 4. 세 번 다 전체 59건 중 1건만 실패했다.

세 테스트가 그동안 이 문제들을 막고 있었습니다. 그런데 **직접 재현해 보기 전에는 이 테스트들이 무엇을 지키는지 몰랐습니다.** 테스트 이름은 읽었지만 그 이름이 가리키는 장애를 본 적이 없었기 때문입니다.

## Part 5. 마치며

MDC를 붙이는 일 자체는 `put`하고 `%X`로 꺼내는 게 전부였습니다. 30분이면 됩니다. 그런데 그다음에 만난 세 가지는 **에러도 안 나고 평소에는 티도 안 나는** 종류였습니다.

되짚어 보면 이번에 얻은 건 MDC 사용법보다 두 가지 습관에 가깝습니다.

첫째, **재현할 때는 확률을 1로 만든다.** 스레드를 하나로 묶고, 요청에서 오지 않는 작업을 일부러 만들었습니다. 운영에서 낮은 확률로 일어나는 일을 개발 환경에서 매번 일어나게 바꾸는 작업이었습니다.

둘째, **로그의 빈칸과 채워진 칸을 비교한다.** 무엇이 남았고 무엇이 사라졌는지가 "누가 넣었는지"를 알려 줍니다. 세 번 다 이 방법으로 범인을 좁혔고, 세 번 다 `MdcScope`는 결백했습니다.

아직 못 한 것도 적어 둡니다. 여기까지는 서버 한 대 기준입니다. 인스턴스를 늘리면 traceId가 있어도 **어느 서버 로그를 볼지**를 모릅니다. 그리고 로그를 콘솔 밖으로 내보내는 구간, 그러니까 비동기 로깅에서 큐가 가득 찼을 때 무슨 일이 생기는지는 따로 재보고 있습니다. 그건 다음 글로 정리하려 합니다.

정상 동작하는 것처럼 보이는 코드에서 문제를 찾으려면 결국 직접 부수고 돌려 보는 수밖에 없다는 걸 배웠습니다. 긴 글 읽어 주셔서 감사합니다.
