## Part 1. 개요

동시에 여러 요청이 들어오면 로그가 뒤섞여 요청 하나의 흐름을 따라갈 수 없습니다. MDC로 요청 식별자를 붙여 이 문제를 해결했는데, 도입한 뒤에 세 가지 문제를 다시 만났습니다. 셋 다 에러가 나지 않고 평소에는 티도 나지 않는 종류였습니다.

이 글은 그 세 가지를 어떻게 재현했고 무엇을 고쳤는지에 대한 기록입니다.

다루는 대상은 아래 주문 흐름입니다. 마지막 알림만 다른 스레드에서 실행됩니다.

```text
HTTP 요청 → 재고 차감 → 결제 → [트랜잭션 커밋] → 알림 발송(@Async)
└──────────── 톰캣 스레드 ────────────┘            └─ 알림 전용 스레드
```

## Part 2. MDC 도입까지

### 2.1 동시 요청에서 흐름이 끊기는 지점

하나는 결제 성공, 하나는 결제 거절인 주문 두 건을 동시에 보내고 로그를 봤습니다.

```text
INFO [http-nio-8080-exec-2] OrderService        - Order created: productId=2, quantity=1, totalPrice=489000.00
INFO [http-nio-8080-exec-3] OrderService        - Order created: productId=1, quantity=2, totalPrice=258000.00
INFO [http-nio-8080-exec-2] FakePaymentClient   - Fake payment requested: scenario=FAILURE, amount=489000.00
INFO [http-nio-8080-exec-3] FakePaymentClient   - Fake payment requested: scenario=SUCCESS, amount=258000.00
WARN [http-nio-8080-exec-2] OrderService        - Payment failed: reason=결제가 거절되었습니다.
INFO [http-nio-8080-exec-3] OrderService        - Payment approved: transactionId=fake-43983592-...
INFO [notification-1]       NotificationService - Order completion notification sent: orderId=1
```

로그는 잘 찍혔지만, 결제 거절 요청의 흐름만 뽑아낼 수가 없습니다.

`Fake payment requested` 줄에는 주문 번호가 없습니다. 금액만 있으니 같은 금액의 주문이 둘이면 구분할 방법이 사라집니다. 그리고 마지막 줄은 다른 스레드입니다. 위 요청 중 어느 것에서 나왔는지 이어 붙일 수 없습니다.

`[exec-2]` 같은 스레드 이름으로 묶는 방법을 먼저 생각했는데, 두 가지 이유로 안 됩니다. 톰캣은 스레드를 재사용하므로 `exec-2`는 조금 뒤 다른 사용자의 요청을 처리합니다. 그리고 비동기 알림은 애초에 다른 스레드라 그 결과에서 빠져 버립니다.

스레드 이름은 누가 처리했는가이지 무슨 요청인가가 아닙니다. 따라서 **요청 자체**에 식별자를 붙여야 합니다.

### 2.2 파라미터로 전달

주문 번호를 인자로 넘기는 방법을 먼저 시도했습니다. 돌려 보니 잘 됐는데 두 가지가 걸렸습니다.

**결제 클라이언트는 주문 번호로 아무 일도 하지 않습니다.** 오직 로그에 찍으려고 받습니다. 나중에 레이어가 늘어나면 로그 한 줄 때문에 모든 메서드 시그니처에 주문 번호가 따라다니게 됩니다.

**제가 짜지 않은 코드의 로그에는 붙일 방법이 없습니다.** 서버를 띄우고 첫 요청을 보내면 이런 줄이 먼저 나옵니다.

```text
INFO [http-nio-8080-exec-1] [traceId= ] o.s.web.servlet.DispatcherServlet - Initializing Servlet 'dispatcherServlet'
INFO [http-nio-8080-exec-1] [traceId=3fbb2a32...] c.e.t.common.logging.TraceIdFilter - HTTP request started
```

앞줄은 스프링이 찍은 줄입니다. 서블릿 초기화는 필터 체인 바깥에서 일어나기 때문에 제가 짠 로그 필터가 아직 실행되지 않았습니다. 실제 에러를 분석할 때 필요한 줄(예: 스택트레이스, 타임아웃)은 프레임워크나 라이브러리가 찍습니다. 그 코드는 jar 안에 있어 파라미터를 넘길 수 없습니다.

### 2.3 MDC 적용

MDC는 쉽게 말해 스레드마다 하나씩 딸린 Map입니다.

```java
MDC.put("traceId", traceId); // 현재 스레드의 Map에 저장
```

```xml
%X{traceId}  <!-- 현재 스레드의 Map에서 꺼내기 -->
```

요청 하나는 처음부터 끝까지 같은 스레드가 처리하니 입구에서 한 번만 넣어 두면 그 요청이 찍는 모든 로그에 따라붙습니다. 값을 파라미터로 계속 전달하는 게 아니라 스레드에 붙여 두고 로그가 알아서 꺼내 가게 하는 방식입니다.

발급 위치는 요청이 반드시 지나가는 서블릿 필터로 잡았습니다. 필터는 서블릿 규격상 `DispatcherServlet`보다 먼저 실행되므로 컨트롤러에 도달조차 못 하는 요청도 traceId를 갖게 됩니다.

로그 한 줄은 두 부분으로 나뉩니다. 앞쪽은 제가 정한 패턴이고 뒤쪽은 찍는 쪽이 만든 메시지입니다.

```text
INFO [exec-1] [traceId=3fbb2a32] DispatcherServlet - Initializing Servlet ...
└───────── 내가 정한 패턴 ────────┘ └───────────── 찍는 쪽이 만든 메시지 ─────────────┘
```

패턴은 `logback-spring.xml`에서 직접 정합니다. 필터에서 MDC에 값을 넣어 두면 이 패턴이 그 값을 꺼내 모든 로그 줄에 붙여 줍니다.

## Part 3. 도입 이후에 만난 세 가지 문제

### 3.1 재현 환경

세 문제 모두 평소에는 티가 나지 않아 재현을 먼저 설계해야 했습니다.

먼저 각 문제마다 다음과 같이 브랜치를 만들었습니다.

| 브랜치 | 문제 코드 | 문제가 되는 경우 |
|---|---|---|
| `experiment/mdc-no-clear` | `TraceIdFilter` | 요청이 끝나고 MDC를 그대로 두는 경우 |
| `experiment/mdc-no-async-copy` | `AsyncConfig` | 비동기 스레드에게 MDC를 복사해주지 않는 경우 |
| `experiment/mdc-no-executor-restore` | `MdcTaskDecorator` | 비동기 스레드 작업이 끝나고 기존 스레드의 MDC로 복구하지 않는 경우 |

확인은 IntelliJ HTTP Client로 했고, 각 브랜치에 `.http` 파일을 함께 뒀습니다.

여기에 하나가 더 필요했습니다. 톰캣의 기본 최대 스레드 풀 크기는 200개입니다. 요청 두 건이 서로 다른 스레드로 흩어지면 아무 일도 안 일어난 것처럼 보이기 때문에 재현 전용 프로파일을 만들어 스레드를 1개로 고정했습니다.

```yaml
# application-mdcleak.yml
server:
  tomcat:
    threads:
      max: 1
      min-spare: 1
```

운영에서는 스레드가 200개라 확률이 낮아 보일 뿐이고 트래픽이 몰리면 결국 같은 일이 일어납니다.

### 3.2 세 가지 실패 형태

#### 형태 A — 요청 종료 후 남는 값

필터에서 값을 넣기만 하고 정리하지 않으면 어떻게 되는지 봤습니다.

```text
14:03:15.173 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request started
14:03:15.296 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=1 userId=user-AAAA] OrderService  - Order created
14:03:15.348 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=1 userId=user-AAAA] OrderService  - Payment approved
14:03:15.372 INFO [http-nio-8080-exec-1] [traceId=51dd263a... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request completed

14:03:34.607 INFO [http-nio-8080-exec-1] [traceId=23d28a6f... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request started
14:03:34.635 INFO [http-nio-8080-exec-1] [traceId=23d28a6f... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request completed

14:03:44.003 INFO [http-nio-8080-exec-1] [traceId=5d0cdebd... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request started
14:03:44.009 INFO [http-nio-8080-exec-1] [traceId=5d0cdebd... orderId=  userId=user-AAAA] TraceIdFilter - HTTP request completed
```

요청 세 건을 보냈고 1번에만 `X-User-Id` 헤더를 보냈습니다. 2번과 3번 요청은 `X-User-Id`를 보내지 않았는데 `user-AAAA`가 붙어 있습니다. 또한 traceId는 매 요청 바뀌는데 userId는 안 바뀝니다.

필터가 traceId는 무조건 새로 넣는 반면 userId는 헤더가 있을 때만 넣기 때문입니다. 헤더가 없으면 덮어쓰지 않으니 이전 값이 살아남습니다. 덮어쓰지 않는 키만 새는 셈이라 이 버그는 눈에 잘 띄지 않습니다.

또한, 같은 요청 안에서 orderId는 없어졌고 userId는 남았습니다. orderId는 try-with-resources로 감싼 MdcScope가 넣고 빼는 값이라 블록이 끝나면서 제거됐습니다. userId만 남았다는 건 MdcScope는 멀쩡하고 필터가 범인이라는 의미입니다.

#### 형태 B — 비동기 스레드로 넘어가지 않는 값

주문 서비스에서 알림 서비스로 MDC를 복사해주지 않으면 어떻게 되는지 봤습니다.

```text
14:24:32.880 INFO [http-nio-8080-exec-1] [traceId=f028bace... orderId=1 userId=user-AAAA] OrderService        - Order created
14:24:32.936 INFO [http-nio-8080-exec-1] [traceId=f028bace... orderId=1 userId=user-AAAA] OrderService        - Payment approved
14:24:32.939 INFO [notification-1]       [traceId=           orderId=1 userId=user-AAAA] NotificationService - 주문 알림
14:24:32.949 INFO [http-nio-8080-exec-1] [traceId=f028bace... orderId=  userId=user-AAAA] TraceIdFilter       - HTTP request completed
```

알림 서비스의 로그를 보면 orderId와 userId는 있는데, traceId는 없습니다. 코드를 보면 누가 넣었는지가 다릅니다.

| 값 | 누가 넣었나 | 결과 |
|---|---|---|
| `orderId`, `userId` | 리스너가 알림 스레드 안에서 직접 넣음 | 그 스레드에서 보인다 |
| `traceId` | 필터가 요청 스레드에서 넣음 | 물려받아야 하는데 못 받았다 |

MDC는 각 스레드마다 가지는 고유한 공간이고, `http-nio-8080-exec-1` 스레드와 `notification-1` 스레드는 별도의 스레드입니다. 따라서 각각의 MDC는 서로 다른 값을 가지므로 물려받지 못한 것입니다.

#### 형태 C — 작업 종료 후 풀 스레드에 남는 값

알림 서비스의 스레드로 값을 복사해 오도록 고쳤지만, 복사한 값을 그대로 두면 어떻게 되는지 봤습니다.

단, 이 재현에는 조건이 하나 더 붙었습니다. HTTP 요청에서 출발한 알림은 매번 요청 스레드의 MDC를 물려받으므로 앞 작업의 값이 남아 있어도 곧바로 덮어써집니다. 남아 있는 걸 보려면 덮어쓸 값이 없는 작업이 같은 스레드를 써야 합니다.

그래서 알림을 다시 보내는 재시도 배치를 넣었습니다. 해당 코드는 스케줄러가 호출하므로, 호출 시점에 MDC가 비어 있습니다. 또한, 알림 스레드풀도 오류를 보기 위해 1개로 고정했습니다.

서버를 띄우고 주문을 한 건만 보냈습니다. 배치는 4초마다 알아서 돕니다.

```text
14:36:11.570 INFO [notification-1] [traceId=           orderId=  userId=]          NotificationService - batch-retry
14:36:15.577 INFO [notification-1] [traceId=           orderId=  userId=]          NotificationService - batch-retry

14:36:18.840 INFO [http-nio-8080-exec-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] TraceIdFilter       - HTTP request started
14:36:18.931 INFO [http-nio-8080-exec-1] [traceId=3fbb2a32... orderId=1 userId=user-AAAA] OrderService        - Order created
14:36:18.991 INFO [notification-1]       [traceId=3fbb2a32... orderId=1 userId=user-AAAA] NotificationService - 주문 알림
14:36:19.014 INFO [http-nio-8080-exec-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] TraceIdFilter       - HTTP request completed

14:36:19.583 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
14:36:23.590 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
14:36:27.595 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
14:36:31.601 INFO [notification-1] [traceId=3fbb2a32... orderId=  userId=user-AAAA] NotificationService - batch-retry
```

주문 전 배치 두 건은 traceId, orderId, userId 모두 비어 있지만, 주문 후 배치 네 건은 orderId만 없고 나머지는 다 남아있습니다.

orderId는 리스너의 MdcScope가 close()에서 뺐으니 남지 않고, traceId와 userId는 TaskDecorator가 복사해 넣고 되돌리지 않았기 때문에 남은 것입니다.

### 3.3 세 형태의 공통 원인

MDC는 `ThreadLocal` 기반입니다. 스레드마다 저장소가 따로 있고, 스레드는 요청이 끝나도 죽지 않습니다. 이 두 가지에서 세 형태가 갈립니다.

형태 B는 스레드가 서로 격리돼 있어서 값이 넘어오지 않는 경우입니다. 격리는 버그가 아니라 설계입니다. 동시 요청 두 건의 traceId가 서로 안 섞이는 것도 이 덕분이고, 그 대가로 비동기에서 끊깁니다.

형태 A와 C는 반대로 스레드가 죽지 않고 재사용되기 때문에 생깁니다. 같은 원인이 서로 다른 스레드풀에서 나타난 경우입니다. 값을 넘겨주는 문제를 풀고 나면 넘겨준 값을 치우는 문제가 새로 생깁니다.

다만 형태 C가 A보다 나쁩니다. 톰캣 스레드는 다음 요청의 필터가 traceId만큼은 덮어써 주지만, 알림 스레드에는 매 작업마다 덮어써 줄 필터가 없기 때문입니다.

## Part 4. 해결과 검증

### 원칙 1 — 내가 넣은 값만 복원

```java
Map<String, String> previousContext = MDC.getCopyOfContextMap(); // 들어올 때 저장
try {
    MDC.put(TRACE_ID, traceId);
    filterChain.doFilter(request, response);
} finally {
    MDC.clear();
    if (previousContext != null) {
        MDC.setContextMap(previousContext); // 나갈 때 복원
    }
}
```

`MDC.clear()` 한 줄로 끝내지 않고 기존 MDC로 복원했습니다. 그냥 `MDC.clear()`만 하면 이 필터보다 앞서 실행된 다른 필터가 넣어 둔 값까지 지우기 때문입니다. 내가 넣은 것만 되돌리는 게 맞다고 판단했습니다.

### 원칙 2 — 복사 시점과 주입 시점의 분리

스프링은 작업을 스레드풀에 넘기기 직전에 `TaskDecorator`를 통해 끼어들 수 있는 자리를 열어 뒀습니다.

```java
public Runnable decorate(Runnable runnable) {
    // ① 지금 실행된다. 아직 요청 스레드다.
    Map<String, String> callerContext = MDC.getCopyOfContextMap();

    return () -> {
        // ② 나중에 실행된다. 여기는 이미 알림 스레드다.
        Map<String, String> executorContext = MDC.getCopyOfContextMap();
        try {
            replaceContext(callerContext);
            runnable.run();
        } finally {
            replaceContext(executorContext);
        }
    };
}

private void replaceContext(Map<String, String> context) {
    MDC.clear();
    if (context != null) {
        MDC.setContextMap(context);
    }
}
```

바깥과 안쪽이 서로 다른 스레드에서 다른 시점에 실행됩니다. `return () -> {...}`는 지금 실행하라는 뜻이 아니라 이런 작업이 있다는 걸 포장해 넘기는 것이고, 안쪽은 대기줄에서 꺼내질 때 실행됩니다.

그래서 복사는 값이 있는 바깥에서, 붙여넣기는 값이 필요한 안쪽에서 해야 합니다. 복사를 안쪽에서 하면 이미 비어 있는 저장소를 복사하게 됩니다.

### 원칙 3 — 작업 종료 후 원상 복구

위 코드의 `finally`가 형태 C를 막는 부분입니다. 풀 스레드가 원래 갖고 있던 상태를 보관했다가 작업이 끝나면 되돌립니다.

여기서 흔히 저지르는 형태가 하나 있습니다. 되돌리기 없이 호출자가 가진 키만 덮어쓰는 방식입니다.

```java
if (callerContext != null) {
    callerContext.forEach(MDC::put);   // 기존 값을 지우지 않는다
}
```

호출자에게 MDC가 없으면 이 `if`를 건너뜁니다. 덮어쓰지도 않으니 스레드에 남아 있던 값이 그대로 살아 있습니다. 배치처럼 요청에서 오지 않은 작업이 이 경로를 타면 앞 사용자의 traceId를 달고 나옵니다.

이게 traceId가 아예 없는 것보다 나쁩니다. 없으면 모른다로 끝나지만 틀린 값은 조사를 엉뚱한 곳으로 끌고 갑니다. 실제로 `grep 3fbb2a32`를 하면 그 사용자가 하지도 않은 배치 작업 네 건이 딸려 나옵니다.

### 4.4 재현 코드에서 나온 오류

형태 C를 재현하면서 한 번 헛돌았습니다. 배치를 넣고 돌렸는데 로그가 이렇게 나왔습니다.

```text
14:30:13.101 INFO [scheduling-1] [traceId= orderId= userId=] NotificationService - batch-retry
```

스레드 이름이 `notification-1`이 아니라 `scheduling-1`이었습니다. 알림 스레드풀을 거치지 않았으니 아무리 돌려도 재현될 리가 없었습니다.

원인은 `@Async`의 위치였습니다. 제 코드에서 비동기 전환은 `NotificationService`가 아니라 이벤트 리스너에서 일어납니다. 그래서 스케줄러가 서비스를 직접 부르면 동기로 실행됩니다. 배치가 실행기에 직접 제출하도록 고치고 나서야 같은 스레드를 물려받았습니다.

로그의 스레드 이름을 확인하지 않았다면 이 문제는 실제로는 안 일어나나 보다라고 잘못 결론 낼 뻔했습니다.

## Part 5. 마치며

MDC는 `put`하고 `%X`로 꺼내면 동작합니다. 그런데 그다음에 만난 세 가지는 에러도 안 나고 평소에는 티도 안 나서, 코드를 되돌려 직접 돌려보기 전까지는 로그만 봐서 알 수 없었습니다.

재현할 때는 확률을 1로 만들어야 했습니다. 스레드를 하나로 묶고, 요청에서 오지 않는 작업을 일부러 만들었습니다. 운영에서 낮은 확률로 일어나는 일을 개발 환경에서 매번 일어나게 바꾸는 작업이었습니다.

원인을 좁힐 때는 로그의 빈칸과 채워진 칸을 비교했습니다. 무엇이 남았고 무엇이 사라졌는지가 누가 넣었는지를 알려 줍니다. 세 번 다 이 방법으로 찾았습니다.

여기까지는 서버 한 대 기준입니다. 인스턴스를 늘리면 traceId가 있어도 어느 서버 로그를 볼지 모릅니다. 로그를 콘솔 밖으로 내보내는 구간, 비동기 로깅에서 큐가 가득 찼을 때 무슨 일이 생기는지는 따로 재보고 있습니다. 다음 글로 정리하겠습니다.
