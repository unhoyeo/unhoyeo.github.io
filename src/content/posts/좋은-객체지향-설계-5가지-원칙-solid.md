좋은 객체지향 설계 5가지 원칙 SOLID는 각각 다음을 뜻한다.

```java
S - SRP - 단일 책임 원칙 - Single Responsibility Principle
O - OCP - 개방 폐쇄 원칙 - Open Closed Principle
L - LSP - 리스코프 치환 원칙 - Liskov Substitution Principle
I - ISP - 인터페이스 분리 원칙 - Interface Segregation Principle
D - DIP - 의존관계 역전 원칙 - Dependency Inversion Principle
```

> SRP - 단일 책임 원칙
> **한 클래스는 '하나의 책임'만 가져야 한다.**

여기서 하나의 책임이라는 것이 조금 모호하다. 클 수도 있고 작을 수도 있으며, 문맥과 상황에 따라 다를 수도 있다. 여기서의 중요한 기준은 **변경 시 파급 효과**다. 어떤 변경이 있을 때 그로 인한 파급 효과가 작을수록 단일 책임 원칙을 잘 지킨 것이다.

예를 들어 어떤 UI 하나 변경하는데 SQL 코드부터 시작해서 애플리케이션 코드를 다 고쳐야 한다면 잘못 설계된 것이다. 또한 객체를 생성하는 부분과 사용하는 코드를 분리하는 것과, 계층을 나누는 것도 단일 책임 원칙을 지키는 것으로 볼 수 있다.

하지만 책임을 너무 작게, 또는 너무 크게 쪼개지 않도록 주의해야 한다. 한 변경이 있을 때 한 클래스만 고치는 것이 SRP를 잘 지킨 것이다.

> OCP - 개방 폐쇄 원칙
> **소프트웨어 요소는 '확장'에는 열려있으나, '변경'에는 닫혀있어야 한다.**

가장 중요한 원칙이다. 그런데 어떻게 코드의 '변경' 없이 기능을 '확장'할 수 있다는 걸까? 이전 글의 <strong>다형성</strong>을 생각해 보면 답을 알 수 있다. 인터페이스를 구현한 새로운 클래스 하나 만드는 것은 기존 코드를 변경하는 것이 아니다. 하지만 <strong>과연 그럴까?</strong>

```java
public class MemberService {

    private MemberRepository memberRepository = new MemoryMemberRepository();
}
```

해당 코드는 다형성을 활용하여, **역할**(MemberRepository 인터페이스)과 **구현**(MemoryMemberRepository 구현 클래스)을 잘 분리하고 있다.

```java
public class MemberService {

//    private MemberRepository memberRepository = new MemoryMemberRepository();
    private MemberRepository memberRepository = new JdbcMemberRepository();
}
```

하지만 기존의 구현 클래스를 새로운 구현체(JdbcMemberRepository)로 변경하려면 기존 코드를 변경해야 한다. 분명 다형성을 사용했는데 **OCP를 위반**했다. 코드의 변경 없이 확장을 어떻게 할 수 있다는 것일까?

이를 해결하려면 누가 대신 "객체를 생성하고, 연관관계를 맺어줘야 한다." 바로 이것을 **스프링 컨테이너**가 해준다.

> LSP - 리스코프 치환 원칙
> <strong>프로그램 객체는 프로그램의 정확성을 깨뜨리지 않으면서,
> 하위 타입의 인스턴스로 바꿀 수 있어야 한다.</strong>

다형성에서 **하위 클래스는 인터페이스 규약을 다 지켜야 한다**는 뜻이다. 다형성을 지원하기 위해서, 인터페이스를 구현한 구현체를 믿고 쓰려면 이 원칙을 지켜야 한다.

예를 들어, 자동차 인터페이스에 '액셀' 기능이 있다. 이 기능을 구현할 때 **앞으로 가는 자동차**를 만들 수도 있고, **뒤로 가는 자동차**를 만들 수도 있다. 하지만 두 경우 모두 컴파일 오류는 나지 않는다. 하지만 LSP는 단순히 컴파일 단계를 이야기하는 것이 아니다. '액셀을 밟으면 앞으로 가야 한다'는 인터페이스 규약을 무조건 지켜야 한다는 말이다. 자동차의 액셀 기능은 앞으로 가는 기능인데, 이를 뒤로 가도록 구현한다면 LSP를 지키지 않은 것이다. 느리더라도 앞으로 가야 LSP를 지키는 것이다.

> ISP - 인터페이스 분리 원칙
> **특정 클라이언트를 위한 인터페이스 '여러 개'가 범용 인터페이스 '하나'보다 낫다.**

예를 들어, 자동차 인터페이스가 있다. 여기에는 운전과 관련된 기능들도 있고, 정비와 관련된 기능들도 있다. 하지만 자동차라는 인터페이스 하나에 담기에는 너무 크니까, 이를 **운전 인터페이스**와 **정비 인터페이스**로 분리하는 것이다. 이렇게 하면 사용자 클라이언트를 운전자 클라이언트와 정비사 클라이언트로 분리할 수 있다. 만약 정비와 관련된 문제가 생겨서 기능을 바꿔야 하는 경우, 정비 인터페이스와 이를 사용하는 정비사 클라이언트 관련된 부분만 바꾸면 되고 운전 인터페이스와 운전자 클라이언트는 바꿀 필요가 없다.

즉, ISP는 인터페이스에 기능이 너무 많으면 복잡하니, 적당한 크기로 잘 쪼개는 것이 중요하다는 뜻이다. 이렇게 하면 인터페이스가 명확해지고 대체 가능성이 높아진다.

> DIP - 의존관계 역전 원칙
> **프로그래머는 '추상화'에 의존해야지, '구체화'에 의존하면 안 된다.**

OCP와 함께 중요한 원칙이다. 쉽게 말해서 **구현 클래스에 의존하지 말고, 인터페이스에 의존**하라는 말이다. 클라이언트가 인터페이스에 의존해야 유연하게 구현체를 변경할 수 있다. 앞서 얘기한 역할에 의존하라는 것과 똑같은 말이다. OCP에서 나왔던 예제를 다시 보자.

```java
public class MemberService {

    private MemberRepository memberRepository = new MemoryMemberRepository();
}
```

여기서 MemberService는 분명 **MemberRepostiory 인터페이스에 의존**하고 있지만, 동시에 **MemoryMemberRepository 구현 클래스에도 의존**하고 있다. 즉, 이 코드는 DIP를 위반하고 있다.

> 내가 A에 의존한다 = 내가 **A의 존재**를 알고 있다

---

## 정리

- 모든 설계에서 역할과 구현을 분리하자.
- 구현체는 언제든지 유연하게 변경할 수 있도록 해야 한다.
- 이상적으로는 모든 설계에 인터페이스를 부여하자.
- 하지만 인터페이스를 도입하면 **추상화**라는 비용이 발생한다. (런타임 구현 클래스를 보려면 코드를 한 번 더 열어봐야 한다.)
- 기능을 확장할 가능성이 없다면 구체 클래스를 직접 사용하고, 향후 꼭 필요할 때 인터페이스를 도입하는 것도 하나의 방법이다.

객체지향의 핵심은 다형성이지만, **다형성만으로는 OCP, DIP를 지킬 수가 없다**. 스프링은 이를 어떻게 해결했을까?
