기존의 MVC 패턴은 중복 코드, 유지보수의 어려움, 구조 일관성 부족 등의 한계가 존재했다.

이 문제를 해결하기 위해 **프론트 컨트롤러(Front Controller) 패턴**을 점진적으로 도입해 보자. (v1 ~ v5)

> 1️⃣ 프론트 컨트롤러 패턴 v1

## 기존 MVC 패턴의 한계

- 컨트롤러마다 개별적으로 서블릿 클래스를 작성해야 하며, 요청 URL별로 각각 매핑이 필요함
- 이로 인해 서블릿 클래스가 많아지고, 각 컨트롤러에 공통적으로 필요한 로직(예: 인코딩, 인증, 로깅 등)이 중복 처리됨
- 확장이나 변경이 어려워지고, 전반적인 코드 구조의 일관성도 무너지게 됨
- 테스트 관점에서도 서블릿에 종속되기 때문에, 단위 테스트가 어렵고 생산성이 저하됨

---

## 프론트 컨트롤러 패턴 v1: 컨트롤러 진입점의 일원화

**단 하나의 서블릿**(프론트 컨트롤러)이 모든 요청을 받아서 적절한 컨트롤러를 호출하도록 구조를 변경해 보자.

서블릿이었던 컨트롤러는 다음 인터페이스를 구현한 **일반 자바 객체**로 변경하자.

```java
public interface ControllerV1 {
    void process(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException;
}
```

이제 모든 컨트롤러는 이 메서드를 통해 일관된 방식으로 호출되며, 프론트 컨트롤러는 구현체에 의존하지 않고 추상적으로 동작하게 된다.

또한, 컨트롤러마다 매핑했던 요청 URL은 프론트 컨트롤러에서 <strong>Map<요청 URL, 담당 컨트롤러></strong>을 통해 관리하도록 하자.

---

## 컨트롤러 예시 (v1)

```java
public class MemberFormControllerV1 implements ControllerV1 {
    @Override
    public void process(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        String viewPath = "/WEB-INF/views/new-form.jsp";
        request.getRequestDispatcher(viewPath).forward(request, response);
    }
}
```

```java
public class MemberSaveControllerV1 implements ControllerV1 {

    private MemberRepository memberRepository = MemberRepository.getInstance();

    @Override
    public void process(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        String username = request.getParameter("username");
        int age = Integer.parseInt(request.getParameter("age"));

        Member member = new Member(username, age);
        memberRepository.save(member);

        request.setAttribute("member", member);

        String viewPath = "/WEB-INF/views/save-result.jsp";
        request.getRequestDispatcher(viewPath).forward(request, response);
    }
}
```

## FrontControllerServletV1 구현

```java
@WebServlet(name = "frontControllerServletV1", urlPatterns = "/front-controller/v1/*")
public class FrontControllerServletV1 extends HttpServlet {

    private Map<String, ControllerV1> controllerMap = new HashMap<>();

    public FrontControllerServletV1() {
        controllerMap.put("/front-controller/v1/members/new-form", new MemberFormControllerV1());
        controllerMap.put("/front-controller/v1/members/save", new MemberSaveControllerV1());
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        String requestURI = request.getRequestURI();
        ControllerV1 controller = controllerMap.get(requestURI);

        if (controller == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }

        controller.process(request, response);
    }
}
```

## 핵심 처리 흐름

1. /front-controller/v1/\* 경로로 들어오는 모든 요청을 프론트 컨트롤러가 수신
2. controllerMap에서 요청 URL에 매핑된 컨트롤러 조회
3. 조회된 컨트롤러의 process() 호출
4. 호출된 컨트롤러는 request/response 객체를 이용하여 로직 수행 후, 뷰 렌더링

## v1 도입 전/후 비교

|  |  |  |
| --- | --- | --- |
| **항목** | **기존 MVC 패턴** | **프론트 컨트롤러 패턴 v1** |
| 컨트롤러 구현 방식 | HttpServlet 직접 구현 | ControllerV1 인터페이스 구현 |
| URL 매핑 | 모든 서블릿에서 개별 매핑 | 단일 서블릿에서 Map으로 일괄 매핑 |
| 유지보수성 | 서블릿 많아짐 → 복잡 ❌ | 일관된 구조 → 관리 쉬움 ✅ |
| 테스트 용이성 | 서블릿에 종속적 → 테스트 어려움 ❌ | 일반 자바 객체 → 테스트 수월 ✅ |

## v1 개선점 요약

- 프론트 컨트롤러에서 공통 로직을 처리할 수 있어, 중복 제거 및 재사용성 증가
- 각각 서블릿이었던 컨트롤러가 일반 자바 객체로 변경되어, 서블릿 종속성 제거 및 테스트성 증가
- 모든 컨트롤러가 ControllerV1 인터페이스를 구현하여, 구조적 일관성 확보
- 컨트롤러마다 URL을 매핑하지 않고 프론트 컨트롤러에서 Map으로 관리하여, 유연한 URL 매핑 처리 가능

> 2️⃣ 프론트 컨트롤러 패턴 v2

## v1 방식의 한계

- 컨트롤러가 '비즈니스 로직'과 '뷰 렌더링' 책임을 동시에 가지고 있어, **관심사의 분리(SoC)가 부족**
- 모든 컨트롤러에서 다음과 같은 뷰 렌더링 코드 중복

```
String viewPath = "/WEB-INF/views/xxx.jsp";
request.getRequestDispatcher(viewPath).forward(request, response);
```

## 프론트 컨트롤러 패턴 v2: 뷰 렌더링 책임 분리

다음과 같은 별도의 **뷰 객체**를 도입하여, 반복되던 뷰 처리 로직을 추상화해 보자.

```java
public class MyView {

    private String viewPath;

    public MyView(String viewPath) {
        this.viewPath = viewPath;
    }

    public void render(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        request.getRequestDispatcher(viewPath).forward(request, response);
    }
}
```

이제부터 뷰 렌더링은 MyView 객체가 담당하므로, 컨트롤러는 비즈니스 로직에 집중할 수 있다.

또한 컨트롤러도 void가 아니라 MyView를 반환하도록 변경하자.

```java
public interface ControllerV2 {
    MyView process(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException;
}
```

컨트롤러가 뷰 경로를 파라미터로 하여 MyView 객체를 생성하여 반환하면, 프론트 컨트롤러가 해당 뷰의 render()를 호출하게 된다.

        return new MyView("/WEB-INF/views/new-form.jsp");

## FrontControllerServletV2 구현

```java
@WebServlet(name = "frontControllerServletV2", urlPatterns = "/front-controller/v2/*")
public class FrontControllerServletV2 extends HttpServlet {

    private Map<String, ControllerV2> controllerMap = new HashMap<>();

    public FrontControllerServletV2() {
        controllerMap.put("/front-controller/v2/members/new-form", new MemberFormControllerV2());
        controllerMap.put("/front-controller/v2/members/save", new MemberSaveControllerV2());
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        String requestURI = request.getRequestURI();
        ControllerV2 controller = controllerMap.get(requestURI);
        if (controller == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }

        // 기존에는 컨트롤러만 호출하고 끝났지만, 이젠 뷰 렌더링도 호출
        MyView view = controller.process(request, response);
        view.render(request, response);
    }
}
```

## v2 개선점 요약

- 컨트롤러는 **비즈니스 로직**, MyView는 **뷰 렌더링**을 담당하여, 관심사를 분리
- 각 컨트롤러마다 중복된 뷰 렌더링 코드 제거
- MyView.render()를 통해 일관된 렌더링 확보, 코드 재사용성 증가

> 3️⃣ 프론트 컨트롤러 패턴 v3

## v2 방식의 한계

- 모든 컨트롤러가 서블릿 기술(HttpServletRequest, HttpServletResponse)에 의존하여, 테스트와 재사용이 어려움
- 컨트롤러가 MyView를 반환할 때, 뷰 이름에 중복 경로가 하드코딩되어 있음 (예: /WEB-INF/views/, .jsp)

## 프론트 컨트롤러 패턴 v3: 서블릿 종속성 제거

컨트롤러에서 서블릿 기술(HttpServletRequest, HttpServletResponse)을 제거하기 위해 다음과 같이 구조를 변경하자.

```java
public interface ControllerV3 {
    ModelView process(Map<String, String> paramMap);
}
```

HttpServletRequest를 제거했으므로, 요청 파라미터를 전달할 때 **Map&lt;String, String> paramMap**을 이용하자.

paramMap은 프론트 컨트롤러에서 다음과 같이 생성한다.

```java
private Map<String, String> createParamMap(HttpServletRequest request) {
    Map<String, String> paramMap = new HashMap<>();
    request.getParameterNames().asIterator()
            .forEachRemaining(paramName ->
                    paramMap.put(paramName, request.getParameter(paramName))
            );
    return paramMap;
}
```

또한 Model 데이터를 저장할 때 request.setAttribute()도 사용하지 못하므로, 데이터는 별도의 Model 객체(ModelView)에 담자.

```java
@Getter
public class ModelView {

    private String viewName; // 논리 뷰 이름
    private Map<String, Object> model = new HashMap<>(); // 저장할 데이터

    public ModelView(String viewName) {
        this.viewName = viewName;
    }
}
```

그리고 데이터뿐만 아니라 논리 뷰 이름도 함께 ModelView에 저장하자. (뷰와 데이터 전달을 하나의 객체로 캡슐화)

기존에는 컨트롤러가 **물리 뷰 이름**을 통해 MyView 객체를 생성 후 반환했지만, 이제는 **논리 뷰 이름**을 통해 ModelView 객체를 생성 후 반환하고, 프론트 컨트롤러가 ModelView 객체에 저장된 논리 뷰 이름을 물리 경로로 변환하여 MyView 객체를 생성하고 렌더링한다.

```java
ModelView mv = controller.process(paramMap); // 이제 컨트롤러는 ModelView를 반환

String viewName = mv.getViewName(); // 논리 뷰 이름
String viewPath = "/WEB-INF/views/" + viewName + ".jsp" // 물리 뷰 이름으로 변환
MyView view = new MyView(viewPath); // MyView 객체 생성

view.render(mv.getModel(), request, response);
```

기존에는 뷰를 렌더링할 때 request에 저장된 데이터를 이용했지만, 지금은 ModelView 객체 안의 model에 데이터를 저장했으므로, MyView.render()에게 model도 추가로 넘겨줘야 한다.

```java
public class MyView {

    private String viewPath;

    public MyView(String viewPath) {
        this.viewPath = viewPath;
    }

    // 기존 버전
    public void render(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        request.getRequestDispatcher(viewPath).forward(request, response);
    }

    // model 추가 버전
    public void render(Map<String, Object> model,
                       HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        model.forEach(request::setAttribute); // model 데이터를 request에 저장
        request.getRequestDispatcher(viewPath).forward(request, response);
    }
}
```

## FrontControllerServletV3 구현

```java
@WebServlet(name = "frontControllerServletV3", urlPatterns = "/front-controller/v3/*")
public class FrontControllerServletV3 extends HttpServlet {

    private Map<String, ControllerV3> controllerMap = new HashMap<>();

    public FrontControllerServletV3() {
        controllerMap.put("/front-controller/v3/members/new-form", new MemberFormControllerV3());
        controllerMap.put("/front-controller/v3/members/save", new MemberSaveControllerV3());
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        String requestURI = request.getRequestURI();
        ControllerV3 controller = controllerMap.get(requestURI);
        if (controller == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }

        // 요청 파라미터는 이제 프론트 컨트롤러가 생성하여 넘겨줌
        Map<String, String> paramMap = createParamMap(request);

        // 기존에는 MyView를 반환했지만, 이젠 ModelView를 반환
        ModelView mv = controller.process(paramMap);

        // MyView는 이제 viewResolver가 생성해줌
        MyView view = viewResolver(mv.getViewName());
        view.render(mv.getModel(), request, response);
    }

    private Map<String, String> createParamMap(HttpServletRequest request) {
        Map<String, String> paramMap = new HashMap<>();
        request.getParameterNames().asIterator()
                .forEachRemaining(paramName ->
                        paramMap.put(paramName, request.getParameter(paramName))
                );
        return paramMap;
    }

    private MyView viewResolver(String viewName) {
        return new MyView("/WEB-INF/views/" + viewName + ".jsp"); // 논리 뷰 이름 → 물리 경로
    }
}
```

## v2 vs v3 비교 요약

|  |  |  |
| --- | --- | --- |
| **항목** | **v2** | **v3** |
| 서블릿 기술 | 컨트롤러에서 직접 사용 (request/response) | 제거됨 (POJO 컨트롤러) |
| 요청 파라미터 | request.getParameter() 직접 호출 | paramMap 전달 |
| 모델 처리 | request.setAttribute() 직접 호출 | ModelView 객체 사용 |
| 뷰 이름 | 물리 경로 하드코딩 | 논리 이름 사용, 물리 경로는 viewResolver가 처리 |
| 테스트 용이성 | ❌ 낮음 | ✅ 높음 |

---

## v3 개선점 요약

- 컨트롤러의 서블릿 종속성을 제거하여, 테스트 용이성 증가
- 별도의 Model 객체(ModelView)를 사용하여, 데이터와 논리 뷰 이름을 하나의 객체로 캡슐화
- 컨트롤러가 물리 뷰 이름 대신 논리 뷰 이름을 이용하여, 하드코딩 제거
- 실제 뷰 경로는 프론트 컨트롤러의 viewResolver()가 처리하여, 뷰 경로 일괄 관리 가능

> 4️⃣ 프론트 컨트롤러 패턴 v4

## v3 방식의 한계

- 컨트롤러에서 ModelView 객체를 매번 생성하고 반환해야 함
- 반드시 ModelView의 구조(논리 뷰 이름, 모델)를 따라야 하므로 **유연성이 떨어짐**
- 즉, 프레임워크의 구조에 컨트롤러 로직이 끌려감

## 프론트 컨트롤러 패턴 v4: ModelView 종속성 제거

ModelView 객체를 사용하지 않도록, 컨트롤러 구조를 다음과 같이 변경해 보자.

```java
public interface ControllerV4 {
    String process(Map<String, String> paramMap, Map<String, Object> model);
}
```

Model 데이터를 ModelView 객체를 생성한 후 model에 저장하는 것이 아니라, 파라미터에서 전달된 model에 저장하자.

또한 ModelView 객체를 생성하여 반환하는 것이 아니라, 단순히 **논리 뷰 이름(String)만 반환**하자.

이로써 컨트롤러가 프레임워크 구조에 끌려가지 않게 된다.

        return "new-form";
    }

## FrontControllerServletV4 구현

```java
@WebServlet(name = "frontControllerServletV4", urlPatterns = "/front-controller/v4/*")
public class FrontControllerServletV4 extends HttpServlet {

    private Map<String, ControllerV4> controllerMap = new HashMap<>();

    public FrontControllerServletV4() {
        controllerMap.put("/front-controller/v4/members/new-form", new MemberFormControllerV4());
        controllerMap.put("/front-controller/v4/members/save", new MemberSaveControllerV4());
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        String requestURI = request.getRequestURI();
        ControllerV4 controller = controllerMap.get(requestURI);
        if (controller == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }

        Map<String, String> paramMap = createParamMap(request);
        Map<String, Object> model = new HashMap<>();

        // model은 이제 프론트 컨트롤러가 넘겨주고, 컨트롤러는 단순히 논리 뷰 이름만 반환
        String viewName = controller.process(paramMap, model);

        MyView view = viewResolver(viewName);
        view.render(model, request, response);
    }

    // createParamMap() 및 viewResolver()는 v3와 동일
}
```

## 핵심 처리 흐름

1. 프론트 컨트롤러가 요청 URL에 매핑된 컨트롤러를 찾고, paramMap과 model 생성
2. 컨트롤러는 선택적으로 model에 데이터 저장 후, 논리 뷰 이름 반환
3. viewResolver가 논리 뷰 이름을 실제 물리 경로로 변환하여 MyView 객체 생성
4. MyView.render()로 뷰 렌더링

- 컨트롤러의 ModelView 종속성을 제거하고, 단순히 논리 뷰 이름만 반환하도록 하여, 코드 간결화

- 개발의 실용성이 강조되어 컨트롤러 구현이 단순함

## v3와 v4 구조의 한계

- v3는 ControllerV3, v4는 ControllerV4에 의존하므로, 프론트 컨트롤러는 한가지 타입의 인터페이스만 처리 가능
- 새로운 방식의 컨트롤러를 도입하려면, 그에 맞는 **프론트 컨트롤러 자체를 새로 만들어야 함**

실무에서는 다양한 방식의 컨트롤러를 요구하므로, 이 모든 것을 하나의 프론트 컨트롤러로 처리하려면 유연한 구조가 필요하다.

## 프론트 컨트롤러 패턴 v5: 어댑터(Adapter) 패턴의 도입

하나의 프론트 컨트롤러가 다양한 컨트롤러를 처리할 수 있도록 프론트 컨트롤러의 구조를 변경해 보자.

> 이제부터 기존의 '**컨트롤러**'라는 명칭 대신 '**핸들러**'라는 포괄적인 용어를 사용하자.
> 어댑터가 지원하기만 하면 컨트롤러뿐만 아니라 무엇이든 URL에 매핑해서 사용할 수 있기 때문이다.

핸들러마다 다른 방식의 입출력을 일관된 형식으로 처리하기 위한 **핸들러 어댑터**를 다음과 같이 구성하자.

```java
public interface MyHandlerAdapter {

    // 해당 핸들러를 처리할 수 있는 어댑터인지 확인
    boolean supports(Object handler);

    // 실제 핸들러를 호출하고, 그 결과로 ModelView 반환
    ModelView handle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws ServletException, IOException;
}
```

우선 어댑터가 해당 핸들러를 처리할 수 있는지 supports(handler) 메서드로 확인하고,

만약 처리할 수 있다면 **handle(request, response, handler)** 메서드를 통해 해당 핸들러를 호출한다.

> 기존에는 **프론트 컨트롤러**가 실제 핸들러(컨트롤러)를 호출했지만, 이제는 **어댑터**가 호출한다.

handle() 메서드는 각 핸들러의 입출력에 맞춰 유연하게 처리하도록 구현하면 된다.

이로써 프론트 컨트롤러는 핸들러를 어떻게 처리할지 고민하지 않아도 된다.

그저 해당 핸들러를 처리할 수 있는 어댑터를 찾고, 어댑터에게 핸들러를 넘겨주면 어댑터가 알아서 처리한다.

**FrontControllerServletV5 구현**

```java
@WebServlet(name = "frontControllerServletV5", urlPatterns = "/front-controller/v5/*")
public class FrontControllerServletV5 extends HttpServlet {

    private final Map<String, Object> handlerMappingMap = new HashMap<>();
    private final List<MyHandlerAdapter> handlerAdapters = new ArrayList<>();

    public FrontControllerServletV5() {
        initHandlerMappingMap();
        initHandlerAdapters();
    }

    private void initHandlerMappingMap() {
        handlerMappingMap.put("/front-controller/v5/v3/members/new-form", new MemberFormControllerV3());
        handlerMappingMap.put("/front-controller/v5/v3/members/save", new MemberSaveControllerV3());
        handlerMappingMap.put("/front-controller/v5/v4/members/new-form", new MemberFormControllerV4());
        handlerMappingMap.put("/front-controller/v5/v4/members/save", new MemberSaveControllerV4());
    }

    private void initHandlerAdapters() {
        handlerAdapters.add(new ControllerV3HandlerAdapter());
        handlerAdapters.add(new ControllerV4HandlerAdapter());
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        // handlerMappingMap에서 해당 요청 URL에 매핑된 핸들러를 찾음
        Object handler = getHandler(request);
        if (handler == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }

        // handlerAdapters 리스트에서 해당 핸들러를 처리할 수 있는 어댑터를 찾음
        MyHandlerAdapter adapter = getHandlerAdapter(handler);

        // 어댑터 호출 → 어댑터가 실제 핸들러를 호출해서 ModelView 반환
        ModelView mv = adapter.handle(request, response, handler);

        // ModelView에서 논리 뷰 이름을 꺼내서 viewResolver 호출
        MyView view = viewResolver(mv.getViewName());
        view.render(mv.getModel(), request, response);
    }

    private Object getHandler(HttpServletRequest request) {
        String requestURI = request.getRequestURI();
        return handlerMappingMap.get(requestURI);
    }

    private MyHandlerAdapter getHandlerAdapter(Object handler) {
        for (MyHandlerAdapter adapter : handlerAdapters) {
            if (adapter.supports(handler)) {
                return adapter;
            }
        }
        throw new IllegalArgumentException("Handler adapter not found for handler: " + handler);
    }

    private MyView viewResolver(String viewName) {
        return new MyView("/WEB-INF/views/" + viewName + ".jsp");
    }
}
```

## 핵심 처리 흐름

1. **핸들러 조회**: 요청 URL에 매핑된 핸들러(ControllerV3, ControllerV4 등)를 찾음
2. **어댑터 조회**: 등록된 어댑터 중 해당 핸들러를 처리할 수 있는 어댑터를 찾음
3. **핸들러 실행**: 어댑터가 핸들러를 실행하여 ModelView 반환
4. **뷰 렌더링**: viewResolver()로 JSP 경로 변환 후 렌더링 수행

## v5 결론 - 프레임워크 수준의 유연성과 확장성 확보

- v5 구조는 실무 환경에서 요구되는 <strong>다형성, 확장성, 개방폐쇄 원칙(OCP)</strong>을 충실히 반영
- 어댑터 패턴을 통해 다양한 컨트롤러를 일관된 방식으로 처리
- 새로운 방식의 컨트롤러가 등장해도 어댑터만 추가하면 프론트 컨트롤러는 변경 없이 재사용 가능
- 프론트 컨트롤러는 "핸들러가 어떤 타입인지", "어떤 방식으로 실행되는지"를 몰라도 됨
- 이 구조는 **Spring MVC의 DispatcherServlet 기반 아키텍처**와 거의 동일하며, 실질적인 MVC 프레임워크의 기본 골격이다.

> 어댑터가 없었다면, 프론트 컨트롤러에서 핸들러 타입에 따라 직접 분기처리를 해야 했을 것이다.

> 버전별 비교 정리

|  |  |  |  |
| --- | --- | --- | --- |
| **버전** | **핵심 개선점** | **컨트롤러 반환** | **모델 처리 방식** |
| V1 | 프론트 컨트롤러 도입 | 없음 (void) | request.setAttribute() 직접 사용 |
| V2 | 뷰 렌더링 분리 | MyView | request.setAttribute() 직접 사용 |
| V3 | 서블릿 종속 제거 + 뷰 논리 이름 도입 | ModelView | ModelView 객체 내부에 model 저장 |
| V4 | 실용적이고 단순한 컨트롤러 | 논리 뷰 이름 (String) | 파라미터로 전달된 model을 직접 조작 |
| V5 | 어댑터 도입 통한 유연한 확장 구조 | ModelView | 어댑터가 컨트롤러에 맞게 처리 방식 결정 |

## v1: 컨트롤러 진입점의 일원화

- 도입 배경:
  - 컨트롤러마다 개별적으로 서블릿 클래스 작성, 개별적으로 URL 매핑
  - 컨트롤러 공통 처리 로직(인코딩, 인증, 로깅 등) 중복
- 개선점:
  - 컨트롤러는 일반 자바 객체로, 서블릿 구현과 URL 매핑은 프론트 컨트롤러에서만
  - 프론트 컨트롤러가 모든 요청 받아서 공통 로직 처리 후, 적절한 컨트롤러 호출

## v2: 뷰 렌더링 책임 분리

- 도입 배경:
  - 컨트롤러에 너무 많은 책임 (비즈니스 로직, 뷰 렌더링)
  - 뷰 렌더링 코드 중복
- 개선점:
  - 컨트롤러는 비즈니스 로직에 집중, 뷰 렌더링은 MyView 객체로 분리
  - 관심사의 분리

## v3: 서블릿 종속성 제거 + ModelView 객체 추가

- 도입 배경:
  - 컨트롤러가 서블릿 기술에 의존
  - MyView 생성 시 물리 경로 중복 + 하드코딩
- 개선점:
  - 프론트 컨트롤러가 요청 파라미터를 Map으로 정리해서 컨트롤러에게 넘겨줌

  - 실제 물리 뷰 경로 변환은 프론트 컨트롤러의 viewResolver에서 일괄 처리
  - viewResolver가 MyView 객체를 생성하여 뷰 렌더링

## v4: ModelView 종속성 제거

- 도입 배경:
  - 컨트롤러에서 매번 ModelView 객체 생성
  - ModelView 구조에 종속적
- 개선점:
  - 프론트 컨트롤러에서 요청 파라미터 Map과 Model 데이터 저장을 위한 Map 전달
  - ModelView 생성 없이, 단순히 파라미터로 넘어온 Map에 데이터 저장
  - ModelView 반환 대신, 논리 뷰 이름(String) 반환
  - 개발자의 편의성 극대화

## v5: 어댑터 패턴 도입

- 도입 배경:
  - 한가지 방식의 컨트롤러만 처리 가능한 프론트 컨트롤러
- 개선점:
  - 프론트 컨트롤러는 해당 컨트롤러(핸들러)를 처리할 수 있는 어댑터만 조회해서 호출
  - 컨트롤러(핸들러)는 어댑터가 알아서 처리하여 ModelView 반환
  - 프론트 컨트롤러는 컨트롤러(핸들러)의 구체적인 형태를 몰라도 됨
  - 새로운 컨트롤러(핸들러)가 추가되어도 어댑터만 추가하면 유연하게 처리 가능
