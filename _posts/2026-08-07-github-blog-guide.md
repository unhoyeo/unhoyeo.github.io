블로그를 하나 만들어야겠다고 마음먹고 검색을 시작하면 이상한 일이 벌어집니다. 분명 "글 쓰는 곳"을 찾고 있었는데 어느새 Ruby 버전 문제를 검색하고 있고, 테마 CSS를 만지고 있고, 정작 글은 한 줄도 안 썼습니다.

깃헙 블로그를 시작할 때 제일 먼저 잡아야 하는 건 테마도 도구도 아니고 **구조에 대한 감각**입니다. 이게 잡히면 나머지는 다 검색으로 해결되고, 이게 안 잡히면 뭘 해도 계속 헤맵니다.

그래서 이 글은 "따라 하면 되는 설치 가이드"보다는 "이게 대체 어떤 구조인가"를 먼저 설명합니다.

## 한 문장으로 말하면

깃헙 블로그에서 글을 발행한다는 건 이런 뜻입니다.

```
마크다운 파일 작성 → git commit → git push → 자동 빌드 → 사이트 반영
```

**글쓰기가 곧 커밋입니다.**

네이버 블로그나 티스토리처럼 웹 에디터에 들어가서 쓰고 "발행" 버튼을 누르는 게 아닙니다. 에디터에서 `.md` 파일을 하나 만들고, 커밋하고, 푸시합니다. 그러면 1~2분 뒤에 사이트에 글이 올라와 있습니다.

이 한 줄이 이해되면 절반은 끝났습니다. 나머지는 이 흐름을 구성하는 부품들 이야기입니다.

## 부품은 세 개뿐입니다

깃헙 블로그라는 단어 하나에 사실 세 가지가 섞여 있습니다. 이걸 분리해서 보는 게 중요합니다.

**1. 깃헙 저장소** — 글(마크다운)과 설정 파일이 사는 곳입니다. 그냥 평범한 git 저장소예요. 특별할 게 없습니다.

**2. GitHub Pages** — 저장소에 있는 정적 파일(HTML/CSS/JS)을 무료로 웹에 띄워주는 깃헙 기능입니다. 서버도, 호스팅 비용도, 배포 스크립트도 필요 없습니다. 켜기만 하면 됩니다.

**3. 정적 사이트 생성기(SSG)** — 이게 핵심입니다. HTML을 직접 쓰기는 싫으니, 마크다운으로 글을 쓰면 목록 페이지 만들고 태그 붙이고 레이아웃 입혀서 HTML로 변환해주는 도구입니다. Jekyll, Hugo, Astro 같은 것들이죠.

정리하면 이렇습니다.

> 마크다운을 **저장소**에 넣으면 → **생성기**가 HTML로 만들고 → **Pages**가 그걸 웹에 띄운다

많은 사람이 헤매는 이유는 이 셋을 한 덩어리로 보기 때문입니다. 문제가 생겼을 때 "빌드가 안 된 건지, 배포가 안 된 건지, 글 파일이 잘못된 건지"를 구분할 수 있으면 트러블슈팅이 훨씬 쉬워집니다.

## 저장소 이름이 곧 주소입니다

여기엔 규칙이 하나 있습니다.

- 저장소 이름을 `아이디.github.io` 로 만들면 → `https://아이디.github.io`
- 아무 이름(`my-blog`)으로 만들면 → `https://아이디.github.io/my-blog`

블로그가 목적이라면 첫 번째를 권합니다. 주소가 짧고 깔끔하고, 나중에 개인 도메인을 붙이기도 자연스럽습니다. 이 이름의 저장소는 계정당 하나만 만들 수 있으니 아껴 쓰세요.

## 생성기는 뭘 고를까

세 개만 놓고 비교하면 충분합니다.

| | Jekyll | Hugo | Astro |
|---|---|---|---|
| 언어 | Ruby | Go | JS/TS |
| 깃헙 지원 | 네이티브 | Actions 필요 | Actions 필요 |
| 한국어 자료 | 압도적으로 많음 | 많음 | 적당 |
| 로컬 환경 | Ruby 세팅이 번거로움 | 바이너리 하나 | npm |
| 대표 테마 | Chirpy, minimal-mistakes | PaperMod | 공식 blog 템플릿 |

**목적이 글쓰기라면 Jekyll + Chirpy를 추천합니다.**

성능이나 최신성만 보면 Hugo나 Astro가 낫습니다. 그런데 실제로 블로그를 포기하게 만드는 건 빌드 속도가 아니라 **막혔을 때 검색이 안 되는 상황**입니다. Jekyll은 한국어 트러블슈팅 글이 압도적으로 많아서, 에러 메시지를 복사해 붙이면 대체로 답이 나옵니다.

Chirpy 테마를 고르는 이유도 비슷합니다. 다크모드, 태그, 카테고리, 검색, 목차, 댓글이 전부 기본으로 들어 있습니다. 커스터마이징을 안 해도 이미 쓸 만한 상태라서, "테마 만지느라 글을 못 쓰는" 함정을 피하기 좋습니다.

프론트엔드에 익숙하고 블로그 자체를 만지는 게 재미있다면 Astro도 훌륭한 선택입니다. 다만 그건 취미가 하나 더 늘어나는 쪽에 가깝습니다.

## 시작하는 가장 짧은 경로

Chirpy 기준으로 이렇습니다.

1. [Chirpy Starter](https://github.com/cotes2020/chirpy-starter) 에서 **Use this template** 클릭
2. 저장소 이름을 `아이디.github.io` 로 생성
3. `_config.yml` 에서 제목, 깃헙 아이디, 타임존(`Asia/Seoul`) 수정
4. 저장소 **Settings → Pages → Source** 를 **GitHub Actions** 로 변경
5. 푸시하면 Actions가 자동으로 빌드 → 몇 분 뒤 접속

4번을 빠뜨려서 "빈 화면이 나온다"고 헤매는 경우가 정말 많습니다. Source가 기본값(Deploy from a branch)으로 남아 있으면 빌드 결과가 아니라 원본 파일이 그대로 서빙됩니다.

로컬 미리보기는 처음엔 건너뛰어도 됩니다. 글 몇 편 올리고 나서 "매번 푸시하고 기다리기 귀찮다" 싶을 때 `bundle exec jekyll serve` 로 `localhost:4000` 을 띄우면 됩니다. 순서를 이렇게 잡는 게 중요합니다. 로컬 환경 세팅부터 시작하면 Ruby 버전 문제로 첫날이 통째로 날아갈 수 있거든요.

## 글 한 편 쓰는 실제 과정

`_posts/` 폴더에 **`YYYY-MM-DD-제목.md`** 형식으로 파일을 만듭니다. 파일명의 날짜가 곧 게시일이 됩니다.

`_posts/2026-08-07-first-post.md`:

```markdown
---
title: 가격 추적 앱을 만들며 배운 것
date: 2026-08-07 21:00:00 +0900
categories: [개발, 사이드프로젝트]
tags: [price-tracker, 기획]
---

## 문제

본문을 마크다운으로 씁니다. 코드블록, 이미지, 표 전부 됩니다.
```

맨 위 `---` 사이에 있는 게 **front matter**, 즉 글의 메타데이터입니다. 제목·날짜·카테고리·태그가 여기 들어가고, 생성기가 이걸 읽어서 목록 페이지와 태그 페이지를 자동으로 만들어 줍니다. 그 아래는 그냥 마크다운 본문입니다.

다 썼으면:

```bash
git add .
git commit -m "post: 가격 추적 앱 회고"
git push
```

끝입니다. 1~2분 뒤 사이트에 올라와 있습니다.

## 쓰다 보면 마주치는 것들

**이미지** — `assets/img/` 에 넣고 `![설명](/assets/img/foo.png)` 로 참조합니다. 다만 이미지가 저장소에 그대로 쌓이면 clone이 점점 무거워집니다. 스크린샷을 많이 쓴다면 압축하는 습관을 들이거나, 외부 호스팅을 쓰는 것도 방법입니다.

**댓글** — 정적 사이트라 DB가 없습니다. 그래서 **giscus** 를 씁니다. 깃헙 Discussions를 댓글 저장소로 쓰는 방식이라, 댓글을 남기려면 깃헙 계정이 필요합니다. 개발 블로그라면 오히려 자연스럽고, 스팸이 거의 없다는 장점이 있습니다.

**초안** — `_drafts/` 폴더에 두면 게시되지 않습니다. 다 쓰면 `_posts/` 로 옮기면서 파일명 앞에 날짜를 붙이면 됩니다. 쓰다 만 글을 마음 편히 커밋해둘 수 있어서 은근히 유용합니다.

**도메인** — 도메인을 사서 DNS를 설정하고 Settings → Pages에 입력하면 `blog.내도메인.com` 같은 주소를 쓸 수 있습니다. 나중에 다른 플랫폼으로 옮기더라도 주소가 유지된다는 게 진짜 이점입니다.

**제약** — 저장소 1GB, 월 트래픽 100GB 권장 한도. 개인 블로그로 넘길 일은 사실상 없습니다. 다만 하나 기억할 것: **저장소를 private으로 만들어도 Pages 사이트 자체는 공개**입니다. 비공개 글이라는 개념이 없으니 민감한 내용은 올리지 마세요.

## 안 맞을 수도 있습니다

솔직하게 적자면, 깃헙 블로그가 모두에게 정답은 아닙니다.

**잘 맞는 경우** — 글이 전부 마크다운 텍스트라 소유권이 온전히 내 것입니다. 버전 관리가 되니 언제 뭘 고쳤는지 남고, 광고가 없고, 나중에 Hugo든 Astro든 다른 플랫폼으로 옮기기도 쉽습니다. 개발 기록이나 포트폴리오 목적이라면 이만한 게 없습니다.

**안 맞는 경우** — 검색 유입이 네이버나 티스토리보다 약합니다. 방문자 수 자체가 목적이라면 아쉬울 수 있습니다. 또 커밋 없이 폰으로 짧은 글을 툭 던지는 식의 가벼운 글쓰기와는 궁합이 안 좋습니다.

즉 **"기록을 남기고 싶다"** 에는 잘 맞고, **"많이 읽히고 싶다"** 에는 덜 맞습니다.

## 마무리

깃헙 블로그의 진입장벽은 대부분 기술이 아니라 **구조를 몰라서 생기는 막막함**입니다.

저장소에 마크다운을 넣고, 생성기가 HTML로 바꾸고, Pages가 띄워준다. 그리고 글쓰기는 곧 커밋이다. 이 두 문장만 잡고 있으면 나머지는 검색으로 다 해결됩니다.

테마를 고르는 데 며칠을 쓰기보다, 오늘 템플릿 하나 복사해서 첫 글을 올려보는 편이 훨씬 빠릅니다. 어차피 테마는 나중에 바꿔도 글은 그대로 남으니까요.
